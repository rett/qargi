# Verification and retries

Every newly prepared run has private, lead-owned attempt state under `<state>/attempts/ID`. Preparation records the original refs, epoch, base branch and base commit before publishing `lifecycle: 1` in the lead's registry. Those prepared values remain immutable. The initial attempt can accept an external read-only report without any runtime dispatch: store the message with `qargi review save RUN`, then run `qargi local verify RUN`.

`qargi local run RUN --again` opens another strict attempt after a completed dispatch or a verified result. The pre-dispatch comparison can accept legitimate lead moves since verification; the accepted refs become the new attempt's baseline. During that attempt, an unjournaled local fast-forward is refused again. Qargi's journaled moves, permitted tracking-ref updates and the project's declared owned refs retain their existing rules. Remote changes still require the existing journal rules.

Dry-run, invalid configuration and other preflight refusals preserve earlier output and verification. Once dispatch crosses the mutation boundary, it first commits the new attempt and clears verification mirrors, then writes dispatch metadata, truncates transcripts, rotates reports or starts the runtime. A setup or spawn failure after that boundary leaves a new, unverified `not-started` attempt. The previous saved generation remains private evidence; it is never replaced by the failed attempt's output. An applied, closed or cleaned run cannot be dispatched again; prepare another run.

## Accepting and recovering output

Verification reads the private attempt's baseline, epoch and phase and compares refs in a private temporary directory. `RUN/verified`, `refs.before`, `started` and `dispatch.json` are compatibility and diagnostic files; changing them cannot grant verification or change the prepared base. Apply and the declared scrub use the original prepared base commit.

The retry epoch is captured before collecting its ref snapshot, so journaled lead moves during a slow remote query remain inside the comparison interval. Lead-written report manifests also use the private prepared base commit, never the mutable `refs.before` mirror.

A successful verification saves output under `<state>/runs/ID`. Each save has a fresh lead-created nonce in its `attempt` marker, bound to the prepared identity and attempt number. The previous copy is retained before a replacement is published. The new copy is built privately, renamed into place, then committed as verified without an intervening recovery step. An interrupted save cannot make an older verification accept the replacement. Its failed copy is retained by recovery, and verification from the original run is required again, even if the ref-comparison phase still says `after-verify`.

Repeated live or `--saved` verification of a current generation reuses that accepted output and advances the private comparison snapshot when refs change. An identical observation consumes no verification history; a changed snapshot consumes one historical record but no retained-copy slot. If the original run exists, changed OUT is refused by verify, review check and apply: re-prepare for revised external/session output. Failed, cancelled, lost and not-started dispatches cannot accept output as a new attempt's product. A successful new runtime attempt produces a new generation. Apply always scrubs its private patch copy for lifecycle runs, even after a successful review check; a check of mutable OUT cannot authorize replacement bytes.

Historical lead-owned, non-symlink `runs` directories are tightened to mode 0700 through an anchored descriptor when saving. Stale cleanup never infers discard from an absent current copy: retained generations require explicit discard.

`qargi local verify --saved ID` and `qargi review apply --from-saved ID` require the current verified prepared identity, attempt and generation. A missing copy, wrong marker or interrupted save refuses; a preserved previous attempt is evidence, not a selectable accepted result. Apply from saved output still requires the original run directory to be gone. Keep the original run until verification and collection have succeeded.

Retention is bounded: at most 32 retained copies and 32 historical verification records per attempt, and 256 attempts per prepared run, subject also to the private record size limit. Reaching a limit refuses further transitions instead of deleting evidence. History capacity is checked before publishing a new verification snapshot, so a history-limit refusal creates no orphan snapshot; identical observations still consume nothing. Preserve wanted evidence separately before cleaning and preparing another run. Clean removes the run's current and retained copies and private attempt state; the lifecycle lock inode remains stable, and the run's [outcome receipt](#outcome-receipts) stays.

Save staging is bounded to one `attempts/ID/save.stage` directory. Before copying, the private `save-stage.json` records its device, inode and prepared identity. The lock-owning Python process copies without a child that could outlive it. After SIGKILL, the next locked reconciliation removes only that recorded stage before retrying. A crash between directory creation and its ownership record leaves an unowned stage: retry and cleanup refuse and preserve it for investigation. Unknown historical `.save.*` paths are never adopted or deleted. These bounds count generations and staging directories, not bytes.

Prepare resolves the temporary parent once before creating directories. A symlinked, relative or `..`-containing `QARGI_RUN_TMP` is supported: printed `TMP`, `RUN/tmpdir`, the task, registry and private `work.json` all name the canonical directory. Repointing the alias later does not redirect cleanup. Hidden-path checks still inspect the actual paths.

Prepare records RUN and TMP device/inode identities and their parent identities in private `work.json`; the lead registry must agree with that TMP path. Ordinary clean checks retained evidence and these identities before removing either directory. An authorization refusal preserves TMP bytes, RUN and retained generations. Missing ownership evidence, foreign ownership, symlinks and replaced directories refuse rather than being adopted, including when RUN is already missing.

Authorized clean first records private ownership of the saved and lifecycle directories in `attempts/ID.clean.json`, then atomically renames them to `runs/.clean.ID` and `attempts/ID.clean`. It then renames owned TMP and RUN to sibling `.clean.NAME.IDENTITY` tombstones before deletion, with recorded per-directory phases. A source replacement before staging refuses. Once the original is demonstrably staged or deleted, a new object at its old pathname is preserved and reported; it does not block cleanup of the owned tombstone or registry bookkeeping. A tombstone with the recorded inode and parent also proves staging after a crash between rename and phase commit. Foreign or unowned tombstones still refuse.

Internal TMP (`RUN/tmp`) is checked through the owned original RUN. Before RUN staging, TMP completion is committed; recovery after RUN staging uses that completion and never follows a replacement RUN, including a symlink, to inspect old TMP or tombstone names. Deletion remains anchored to the original parent descriptor and retains the one-filesystem restriction. A legitimate external TMP can be recovered even if RUN is missing; a member-writable `tmpdir` file grants no authority. Only after the exact original registry row commits `cleaned` does cleanup remove saved and lifecycle tombstones; the ownership record is removed last. Rerun `qargi local clean RUN` to finish an interrupted authorized deletion, including one interrupted after marker or lifecycle-state removal. Recovery checks recorded device/inode ownership without requiring a partially deleted marker. No replacement or orphan is adopted. Lifecycle cleanup keeps a cleaned registry row even after the original RUN is lost. Other lifecycle verbs refuse while cleanup is pending.

## Outcome receipts

Clean keeps the facts about a run's outcome that later measurement needs. After every cleanup check has passed and before the cleanup intent is recorded, clean of a lifecycle run writes one outcome receipt, `<state>/attempts/.receipts/ID.PREPARED.json` (mode 600 in a mode 700 directory). `ID` is the run id (`qargi.XXXXXX`). `PREPARED` is the identity that prepare gave this use of the run id: 32 hexadecimal digits, `prepared.identity` in the run's private state. No clean removes the receipt: it outlives the run, its saved copies and its attempt state. No command reads receipts yet and nothing removes them; each is at most 16384 bytes.

To find the receipts of one run, list `<state>/attempts/.receipts/ID.*.json` with its run id, for example `qargi.Ab12Cd.*.json` for the run `qargi.Ab12Cd`. There is normally one. A run id that prepare hands out again, after the registry has stopped naming its earlier use, gets one receipt per use; the prepared identity in the name keeps them apart, and the later use never touches the receipt of the earlier one. The key `run` inside each of them holds the same run id.

The receipt is one JSON object with exactly these keys. A fact that is not recorded, or that does not have its expected form, is `null`; nothing is guessed.

| Key | Value | Source |
|---|---|---|
| `version` | `1` | |
| `run` | the run id (`qargi.XXXXXX`), never its path | |
| `slug`, `role`, `class` | the run's slug, role and class | the lead's registry row |
| `base` | `{branch, commit}`: the feature or base branch name and the base commit | the prepared record |
| `final_commit` | the tip that `qargi review apply` built | the private apply record (`built` or `done`), else `null` |
| `requested` | `{model, effort}`: the model id and effort that prepare resolved | the private prepared request; a `--model` or `--effort` given to `local run` is not in private state and is not shown |
| `observed` | `{model, effort}` | reserved: both are `null` today, because the runtime's observed identity is not recorded in private state. The key and its shape belong to version 1, so a later release can fill it without a new version; read `null` as not recorded |
| `attempts` | one `{n, outcome, started, ended}` per attempt; the last three are `null` for an attempt with no dispatch | the private attempt record |
| `attempt_count` | the number of attempts made | the private attempt record |
| `verification` | `{state, at}`: `verified` or `unverified`, and the time of the verification in force | the current attempt |
| `apply` | `done` or `built` (applied with `qargi review apply`), `closed` (taken by hand, `qargi local close`), `none` | the private apply record, then the registry |
| `done` | `{status, exit_code}`: `DONE` or `BLOCKED`, and the exit status of the DONE check, as the member's manifest records them | `out/manifest.json` of the current verified saved copy |
| `skips` | the number of gates the manifest records as `not run` | the same manifest |
| `deviations` | the number of entries of the manifest's `deviations` | the same manifest |
| `disposition` | `cleaned` (an ordinary clean) or `discarded` (`clean --discard`) | |

A reader decides by `disposition` what a receipt holds, not by its keys or by `version` alone. `cleaned` and `discarded` carry every key of the table. Any other value carries only what its writer could record: today that is `discarded, no receipt`, described below, which has `version` and `run` beside it and nothing else.

The list `attempts` is truncated, not refused: it holds the most recent 64 attempts, and `attempt_count` still counts all of them. A receipt that would exceed the byte limit all the same is refused. The manifest values are the member's claims, read only from the saved copy that verification accepted: an unverified run, a run whose saved copy is not the current verified one, and an unreadable or oversized manifest give `null`. The run directory is never read. The receipt holds no path, credential, token, environment value, task text or report text: registry values are copied only when they have the form of a slug, a role or a class, and the manifest contributes two enumerated values and two counts.

A receipt is provisional until clean records its cleanup intent, and final from then on. It is written whole under a temporary name, synced, and then given its final name with a hard link, which cannot replace an existing file. Its content depends only on recorded state, with no clock reading, so a repeated clean finds the same bytes and writes nothing.

Clean replaces a receipt in one case only: it holds the run's lifecycle lock, no cleanup intent is recorded for the run (`attempts/ID.clean.json` is absent), and the receipt under the run's name holds other bytes than the recorded facts give now. Such a receipt was left by a clean that was interrupted after the receipt and before the intent; since then the run was dispatched, verified, applied or closed again, or the next clean is a `--discard`. That clean writes the current facts under the temporary name, syncs them and renames them over the earlier receipt, so a reader sees the earlier receipt or the new one, never a part of either. Once the intent is recorded nothing rewrites the receipt: a resumed clean starts after the intent, and the clean removes the private state that carries this prepared identity, so no later clean can name the file again. A receipt is therefore provisional only while its run still has its private state (`attempts/ID`, with the same prepared identity) and no `attempts/ID.clean.json`; every other receipt is final.

An ordinary clean that cannot write the receipt (a receipt directory that is not private or not writable, a full file system, or something under the receipt's name that is not a plain private file of the lead, such as a link or a file with another mode) refuses with a message that names the receipt and the cause, before the cleanup intent is recorded: the run, its temporary directory, its saved copies and its attempt state are untouched, and the run remains usable. `clean --discard` goes on in that case. It tries to record `{version, run, disposition}` with the disposition `discarded, no receipt` in the receipt's place, and prints a warning that says why the receipt was not written and whether that disposition was recorded.

An interrupted clean resumes after its recorded intent and never rewrites the receipt, so it ends with the receipt it began with. A clean that is interrupted after the receipt and before the intent leaves the receipt behind and the run usable, and the next clean finds it. When the recorded facts are still the same, that clean writes nothing. When they differ, it replaces the receipt as described above and goes on; it does not refuse.

## Execution, termination and acceptance

Actual dispatch, public verify, apply, close and clean share one nonblocking lifecycle lock. A busy lock refuses promptly, including `clean --discard`. Internal apply/verify and close/clean checks share only the actual held descriptor. Lock order is lifecycle, apply PID lock, then short registry or journal locks. Members, Git helpers, scrub commands and background lease renewers receive no lifecycle descriptor.

The runtime owner records begin, member identity and end itself. Execution completion, termination of the recorded member process group, and verification of returned output are separate decisions. An active or unknown attempt cannot be verified, applied, closed or cleaned. After an owner dies, recovery can mark the attempt `lost` only when the kernel reports the recorded member group absent (`killpg` with signal 0 fails with ESRCH). A member can fork after a `/proc` enumeration and exit before inspection, leaving an unlisted live child. An addressable group with no observed live member remains unknown for completion, recovery, retry and discard.

There is an intentional unknown-spawn window: if the owner dies after begin and no member identity was committed, qargi cannot prove whether a child was launched. Retry, verification and discard refuse with an unknown-liveness diagnostic. Do not edit the record to fabricate an ended member or rely on `dispatch.json` to recover it. Preserve the evidence and investigate outside these lifecycle verbs. This implementation provides no automatic recovery protocol for that window.

Handlers for TERM, HUP and INT are installed before begin. A caught prelaunch signal records an honest `not-started` outcome; SIGKILL and power loss still leave the uncertain window above. A group containing only exited but unreaped processes remains busy or unknown until reaped, consistently with the runner. Its nonzero `group_left` value can stand for unknown membership rather than an exact live-process count. A vanished `/proc/PID/stat`, including Linux `ESRCH` after the process was reaped between open and read, counts as that PID's absence only while `/proc/self/stat` remains available. Other process-evidence errors remain unknown; a missing PID alone never proves its group gone. Hosts that do not reap orphaned zombies may require intervention outside these verbs before retry or cleanup.

An unfinished apply marked `started` cannot be resumed, cleaned or discarded even after its shell dies: Git or a hook may still be alive, and the shell's PID is not evidence of child termination. Preserve its worktree and record for investigation. A `built` apply can still finish its recorded bookkeeping after its owner exits; its Git work has completed. Git and hooks must never inherit the lifecycle lock.

Process evidence is Linux-specific and covers the recorded process group. Descendants can escape it by starting another session; this is not containment of escaped processes. An unavailable or unsupported host process probe is unknown, never proof of termination. Filesystem operations that committed but could not fsync their directory warn; persistence across power loss is not guaranteed.

## Legacy preparation

The current production format is the foundation's schema 1, selected by the exact registry marker `lifecycle: 1`. New command runs add a validated `prepared.request` and registry marker `command_request: 1`; the marker requires that private request and cannot fall back when it is missing or malformed. Existing schema-1 records without requests retain their previous dispatch defaults and validation, with no automatic adoption from RUN or saved files. The private request survives retries; saved `request.json` is generated from it for inspection and grants no recovery or drift-acceptance authority. A genuinely unmarked registered run retains warned inspection and recovery, but actual runtime dispatch requires a newly prepared run. `clean RUN --discard` is explicit weaker recovery: preserve wanted work and establish process safety yourself first. It proves neither process quiescence nor prepare-time directory identity, and never adopts snapshots into lifecycle authority. Ordinary legacy clean retains its original product, refs, worktree, applied/merged and apply-lock checks; `--discard` deliberately drops evidence past the product and inspection checks, but not a held lock. A legacy run has no lifecycle state, so its clean writes no outcome receipt.

Legacy TMP comes from the lead registry, never `RUN/tmpdir`. It is removed only as a non-symlink `qargi-run.XXXXXX` directly under the real `/dev/shm` or configured `QARGI_RUN_TMP` parent (or `RUN/tmp`), using `rm --one-file-system`. Other TMP paths are left and named. This path check records no inode and does not detect a concurrent replacement. A missing legacy RUN follows the released record/saved-copy recovery route and leaves its TMP as an orphan. `clean --applied` and `--stale --yes` use the same ordinary checks; stale recovery keeps unapplied saved work and names explicit discard as the deliberate escape.

A marked run whose state or ownership is missing, corrupt or unsupported fails closed and is never treated as legacy. An unmarked row with private lifecycle remnants also refuses: attempt state, cleanup intents, lifecycle or saved-copy cleanup tombstones, saved attempt markers, or saved records containing a lifecycle marker. These remnants remain evidence, not permission to adopt a run. The stable lifecycle lock alone is not evidence of preparation, since legacy inspections acquire it too.
# Diagnostic inspection and acceptance

Review check can inspect output after an unsuccessful dispatch, including a
truthful BLOCKED report. Its structural verdict is diagnostic and does not
attribute that output to the unsuccessful attempt or accept it. Local verify
and review apply still refuse such output. Changes to already accepted OUT are
refused by check, verify and apply; prepare a new run for revised output.
