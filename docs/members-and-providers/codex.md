# Codex as lead and as member

The local runtime `codex` (`lib/providers/codex.json`, family `openai`) is data only: a member is a `codex exec` process that `qargi local run` starts in the run's clone. Codex as the **lead** (the session you talk to, which loads qargi's skills and runs the `qargi` command) and Codex as a **member** (a headless process that reads `RUN/task.md` and returns qargi's artifacts) are different surfaces; Codex's own subagents are not members and do not replace the prepared clone and the run registry. See [Providers and runtimes](providers.md) for the table of what `codex` is and is not, and [Choosing models](models.md) for its catalog.

What this page says was established with codex-cli 0.167.1 on Linux, unless a section names another version. "Seen offline" means a check with no sign-in, no model call and no network (`codex debug prompt-input`, `codex mcp list --json`, `codex features list`, `codex debug models`, `codex sandbox`, with a scratch `CODEX_HOME`). "Live" means a check with a sign-in and a model call, on a scratch repository. Three capabilities of `codex` are verified live and dated in its definition; the others stay unverified (`verified_on` null) until a live check of `/qargi-providers` (`verify.md`) shows them ([What is verified](#what-is-verified)).

## What is verified

Each verified capability carries `verified_on` (the date of its checks) and `source` (the evidence and the CLI version) in `lib/providers/codex.json`; `qargi provider show codex` prints the date and the note of each, and `--json` the whole definition. All were checked with codex-cli 0.167.1 on 2026-11-11, on the fast tier (`gpt-6-luna`) at `low` effort.

- **Headless dispatch**: Verified: yes; By: `qargi local run` ran `codex exec` for a write-class build task on a scratch repository: the member created and committed a file, the series, manifest and report came back, `qargi local verify` found the refs unchanged, `qargi review check` ended with 0 failures (3 warnings about optional manifest fields), and `qargi review apply` applied the series in a disposable repository, where the DONE command passed
- **Read-only barrier**: Verified: partial; By: offline, `codex sandbox -- sh -c 'echo x > /tmp/p'` answered "Read-only file system"; live, a `codex exec --sandbox read-only --ignore-rules` member (approval policy `never`, its own `CODEX_HOME` and `HOME`) asked to create a file in its working directory reported "Read-only file system" and the directory was unchanged. It holds the member's shell writes, not its reads, and not a hosted tool or an MCP server, which run outside the sandbox: so the claim is `partial`, and a review role runs on it with that note and no `provider accept`
- **Token report**: Verified: partial (tokens only); By: the `turn.completed` events carried the usage counts the definition reads, and the runs printed them as `USAGE=` (input, cached, output and reasoning tokens)

Not verified, and so counted as not supported:

- **The model and effort overrides.** A run with `-m gpt-6-luna` and `-c model_reasoning_effort=low` succeeded, but no event of `codex exec --json` names the model or the effort used (the events are `thread.started`, `turn.started`, `item.completed` and `turn.completed`), so that they take effect is not observable.
- **Skills and MCP.** Interactive skill loading, the complete client skill inventory and the MCP tool names and `enabled_tools` remain unqualified. The headless marker observations below have a narrower scope.
- **The rest of a run.** How codex-cli writes a sign-in it refreshes during a run (through the link, or by replacing it), each baseline key holding in a real run, the hosted tools being gone, and how a trusted project's `.codex/` loads.

On 2026-11-16 UTC, two headless qargi local run fixtures with codex-cli 0.169.0 returned unpredictable skill markers absent from their tasks. The checkout-link run logged reads of SKILL.md and marker.txt and observed CODEX_HOME/skills absent. The opted-in member snapshot returned its marker with no command or tool events in the transcript; its client-file inventory remains unverified self-report. Both runs removed the temporary sign-in link. The snapshot run's managed delivery was removed. Requested gpt-6-luna/low identity remains unattested. These observations qualify marker access for the two fixtures. Interactive lead loading, Desktop sessions, other versions/providers and client writes into the skills directory remain unqualified. The skills capability verification date remains unset. Managed member delivery requires RUN and private state on one Linux filesystem.

## Platform and sandbox

qargi runs on Linux only (see the requirements in the repository's README). On Linux the Codex sandbox is bubblewrap: `codex sandbox -- CMD` runs the command under `codex-linux-sandbox` in a bwrap namespace with a read-only root, a seccomp filter and the network restricted (seen offline). Codex has a different sandbox on macOS; it plays no part here, since qargi does not run there. A read-only member runs under `--sandbox read-only` (nothing writable), a write member under `--sandbox workspace-write` with OUT and the clone's `.git` added as writable directories. Under `workspace-write` Codex keeps the clone's `.git`, `.agents` and `.codex` read-only unless they are added (seen offline), which is why the write class adds `.git` and nothing else.

**Keep the scratch directory off `/dev`.** The sandbox mounts a `/dev` of its own, so nothing under `/dev`, `/dev/shm` included, is there for the member's commands: a read-only member run there sees no clone, no contract and no OUT, and starts in `/`; a write member sees its clone, OUT and TMP, which the sandbox binds in as writable places, but not its contract or its git wrapper beside them (seen offline with `codex sandbox`, and live: a review run under `/dev/shm` returned a useless report, and a build run there worked without ever reading its contract). The definition declares it (`dispatch.hidden_paths`: `/dev`, and the clone, OUT and TMP shown to a write run), so `qargi local prepare` and `qargi local run` refuse such a run before anything is made or started, naming the path, `/dev` and the fix. A `--scratch` under `/dev/shm`, a common place for fast throwaway work, therefore does not work for Codex runs, a read-only one least of all: use a directory on disk under your home, such as `~/.cache/qargi-runs`. The two read-only marker fixtures above ran under `/tmp` with codex-cli 0.169.0. Write-class runs there remain unqualified; the baseline sets `exclude_slash_tmp`. The run's TMP may stay on `/dev/shm`, where `prepare` puts it: a write run's TMP is bound in, and a read-only member writes none.

**Which `codex` runs.** `qargi local run` resolves `codex` on your `PATH`, entry by entry, to the first regular executable file whose real path is named `codex` (or `codex.js`, a launcher a package manager links as `codex`, or `codex-` and a suffix, a release binary such as `codex-x86_64-unknown-linux-musl` linked as `codex`) and starts that path; `--dry-run` prints it as `COMMAND=` and `RUN/dispatch.json` records it as `command`. A version manager's wrapper or shim that is a link to a program of another name is passed over with a note. With `HOME` set to the run home such a wrapper looks for Codex under the run home, or installs it there, and the sandbox's re-exec of Codex then fails, so every shell command of the member fails (seen in a live run). When only such a wrapper is on `PATH` the run is refused (exit 3), naming it: put the directory the version manager installed Codex in first on `PATH`. A shim that is a script named `codex` cannot be told from the program by its name and runs as found. The member's own `PATH` is yours, unchanged, and so are the wrappers on it for other tools: a version manager's `go`, `node` or `python`, and a script whose first line is `#!/usr/bin/env node` that reaches node through one, also run with `HOME` set to the run home, where they may look for their tools, install them or fail, and the member's command fails with them. qargi does not look for these (only the command it starts is resolved). When a member needs such a tool, start the run with a `PATH` whose first entries are the directories the version manager installed the tools in.

## What a member run loads

Managed skill delivery defaults off. The optional owner gate `qargi packs member-skills PROJECT --enable` freezes canonical skills for the actual member role, then copies them into `RUN/home/.codex/skills` for launch. This shipped destination declaration changes no capability date and qualifies no actual loading. Existing prepared requests bind exact provider bytes, so the declaration can stale a request even when delivery stays off: re-prepare. Turning the gate on after prepare also requires re-prepare. [Managed member snapshots](../../skills/qargi-packs/member-skills.md) defines selection, bounds, drift and ownership. Codex has no qargi guard hook; its sandbox and instructions provide only their documented protection. Canonical selection governs the managed snapshot while committed checkout skills and other readable files retain their independent discovery/access behavior.

The run's `config.toml` in `CODEX_HOME` (`RUN/home/.codex/config.toml`) is the user-level configuration of the member's Codex, written by qargi for every run. It is not the only thing Codex reads:

- **your `~/.codex/config.toml`, rules, skills, `AGENTS.md`**: not loaded: `CODEX_HOME` is the run home, which holds what qargi writes (the configuration file, the sign-in link and, when opted in, managed skill copies) and what Codex makes there itself. Not loaded is not unreadable: the member's commands can read them by path ([What a member can reach](#what-a-member-can-reach))
- **`~/.agents/skills`**: not loaded: `HOME` is the run home too
- **the run's `config.toml`**: the baseline below, and the MCP servers of the role's tool packs
- **the clone's `.codex/` (its `config.toml` with MCP servers and settings, `rules`, hooks)**: not loaded: Codex loads a project's `.codex/` only for a trusted project, and a run clone is a fresh path that no configuration marks trusted (the run's file has no `projects` entry). Seen offline: with a trust entry in a scratch home the same repository's MCP server and settings load
- **the clone's `AGENTS.md`**: loaded, as for any Codex session: the repository's own instructions keep working
- **the clone's `.agents/skills`**: loaded (also untrusted): only what the repository commits
- **execpolicy rules files**: none: `--ignore-rules` drops the user's and the project's
- **a system-wide or administrator-managed Codex configuration**: not excluded: qargi cannot keep it out, and it applies to members as it applies to you

The baseline is `dispatch.run_config.baseline` of the definition; a run with no MCP server and a run with one get the same keys (a test compares them key by key), and `--strict-config` makes Codex refuse a key it does not know, so a key a later CLI renames stops the run instead of being ignored.

- **`approval_policy`**: Value: `never`; Why: nobody answers a member; a command the sandbox refuses fails and the member sees the failure (the prompt input says "Approval policy is currently never", seen offline)
- **`sandbox_workspace_write.network_access`**: Value: `false`; Why: no network for the member's shell commands
- **`sandbox_workspace_write.exclude_slash_tmp`**: Value: `true`; Why: `/tmp` is shared with the rest of the machine; a write member writes temporary files in `TMPDIR`
- **`sandbox_workspace_write.exclude_tmpdir_env_var`**: Value: `false`; Why: `TMPDIR`, the run's TMP, stays writable (seen with `codex sandbox`: `/tmp` refused, `TMPDIR` written, no network)
- **`web_search`**: Value: `disabled`; Why: hosted search runs at the vendor, outside the shell sandbox
- **`features.apps`, `plugins`, `remote_plugin`, `hooks`, `computer_use`, `browser_use`, `in_app_browser`, `image_generation`, `tool_suggest`, `skill_mcp_dependency_install`**: Value: `false`; Why: features that reach outside the shell sandbox, install things or run code Codex did not get from the member's commands (`codex features list` shows them off); `image_generation` is off in the baseline of every run and turned on only by the opt-in below
- **`skills.bundled.enabled`**: Value: `false`; Why: the skills Codex ships (an installer, a creator, image generation) are no part of a member's task (the prompt input lists none, seen offline)

Each key is read by this CLI (a value of the wrong type is refused, naming the key). That every key holds in a real run, and that the hosted tools are gone from a real session, is not verified: the offline prompt input shows no hosted tool either way. The multi-agent tools (`spawn_agent` and its kin) stay listed: no supported switch removed them offline.

## Image generation: an opt-in, off by default

`codex-cli` 0.171.0 lists `image_generation` as a stable feature that is on by default (`codex features list`, scratch `CODEX_HOME`, offline); the baseline above turns it off, and a run gets it only when the project's owner opted in. `image_generation_animation` (under development, off) and video are not declared by the definition, so a project cannot enable them: that would be another option and another approval.

The definition declares the option as data, `dispatch.run_config.options.image_generation`: the setting it turns on (`features.image_generation = true`, a baseline `false` set to `true`), the classes it is for (write runs only), that the tool runs outside the sandbox, that it may spend (`unknown`), where it may write, the words the owner's approval must contain (`hosted image generation runs outside the sandbox`) and that it is **not verified** (`verified_on` is null; no run has had the feature on). Three layers decide whether a run has it:

1. the definition declares it (an option that is not declared does not exist);
2. the owner enables it for the project's runtime: `qargi provider enable PROJECT --runtime codex --option image_generation` prints the plan and a token (the TOML lines it adds to the run's `config.toml`, that the hosted tool runs outside the Codex sandbox so the shell's network denial does not hold it, that it may spend on the members' sign-in and that qargi does not measure that, that images reach the clone only if the member saves them there, the reads warning, that it is unverified, the profiles that could select it, and the phrase) and changes nothing; `--plan TOKEN --approved WORDS` stores `models.run_options.local.codex` and the digest of the option's declaration as the plan showed it (`models.run_options.declared.codex.image_generation`), and writes one audit line (`provider:enable-option`). Words without the phrase are `runtime-option-unacknowledged` and the token stays good; the phrase is read as words, a hyphen or an underscore being part of a word, so `xhosted image generation runs outside the sandbox` and `x-hosted image generation runs outside the sandbox` do not carry it. `codex` must already be the project's own runtime or an enabled extra one. `qargi project set` refuses the answer, `project init --answers` and an archive import can drop an option and never add one, and the guard refuses the verb to a member;
3. a profile of the project selects it: `qargi project set PROJECT profiles.NAME.options '["image_generation"]'`, a plain set that only chooses among what the owner enabled for the profile's runtime. `qargi project validate` refuses an option that is not enabled and a profile on the `reviewer` base. There is no `--option` on `qargi local prepare`: a task gets the option only through its profile.

A run of such a profile has `RUN_OPTIONS=image_generation (hosted, outside the sandbox, may spend)` in the `local prepare` output (and again when it runs), `--dry-run` prints `RUN_CONFIG_OPTIONS=` (what each option applies; `RUN_CONFIG_BASELINE=` stays the baseline), its `config.toml` is the baseline with `features.image_generation = true` and nothing else changed, and `RUN/dispatch.json` records `run_config.options` (names only). Every other run of the same project, a read-only run included, gets the baseline alone, and a project that enabled nothing sees no new line or key, and a request that changes only as any edit of the definition changes it (declaring the option moved the definition's hash, so a `codex` run prepared before the upgrade is refused at `local run` as `runtime-drift` and is prepared again). A read-only run whose profile selects the option is refused at prepare (`runtime-option-class`). The option binds the prepared request: enabling, selecting or editing it after prepare makes `local run` ask for a new prepare. The approval binds the declaration too: a definition that changes the option after the owner approved it (its settings, classes, flags, phrase or note) is refused at `local prepare` for a profile that selects it (exit 2), and `qargi project validate` reports it as a finding, until the owner disables the option and enables it again with the plan of what it now is. An option enabled with no recorded digest is refused the same way. `qargi provider disable PROJECT --runtime codex --option image_generation` is refused while a profile selects it, then takes its own plan and token and asks for no phrase.

What qargi does not know: where a generated image lands (the clone, the run home or only the transcript), what events the tool emits, and whether its cost is in the `turn.completed` usage (`cost_report` is tokens only; a ChatGPT sign-in reports no money per run). One live check with a scratch repository, the smallest model and one small image would settle the first two; it spends, so it is asked of the owner first, and it has not been done: the option stays unverified, and the images a run leaves are not yet listed, checked or cleaned by `local list`, `review check` or `local clean`.

## What a member can reach

- **Files.** A write member can write its clone, the clone's `.git`, OUT and `TMPDIR`. With the `.git` it can set what git runs in that clone (a hook, `core.fsmonitor`, an alias, a filter driver), so never run git in a write member's clone: take the work from the patches in OUT, copy files out, or make a clean copy first with `git clone --no-local` (git(1), SECURITY). `qargi local run` compares the clone's `.git/config`, `hooks/` and `info/` before and after the member and names a change in a `GITDIR=changed:` line (it restores nothing). A read-only member can write nothing, OUT and `TMPDIR` included, so a test that needs a temporary file fails in a read-only run. Both can read what your user can read: the sandbox holds writes, not reads. The definition says so (`dispatch.reads`: `confined` false, `exposes` `~/.codex`), and the plan of `qargi provider enable PROJECT --runtime codex` repeats it with the phrase `reads are not confined`, which the owner's approval must carry.
- **Network.** The member's shell commands have none. That is not all the network a run uses: the Codex process itself talks to the model service, and it connects to the MCP servers of the run's file, outside the shell sandbox. Hosted search and apps are off in the baseline (not verified live).
- **Git.** The member's git has no credentials (`HOME` is the run's, no global configuration, no ssh agent, no prompts), the clone's only remote is the run's bare copy with its push URL disabled, and the sandbox gives its commands no network, so an ordinary push has nothing to reach and nothing to authenticate with. That is what qargi supports, not a proof that no push can happen: `qargi local verify` compares snapshots of the real repository's local refs and origin's heads and tags, excluding `refs/qargi/`, and you apply only the patches. See the [local-run architecture](../development/architecture.md#the-life-of-a-local-run) for accepted differences and coverage limits.
- **No guard hook.** No `qargi __guard` runs for a Codex member, so the guard's refusals (push, `gh`, `ssh`, the skill and runtime verbs, writes to protected places) do not apply as such; the sandbox's write and network denial, the credential-free git and the checks of what comes back hold instead.
- **Sign-in.** A member never uses your own Codex sign-in. The run home holds a private copy of the members' sign-in, `~/.codex-members/auth.json`, for the length of the run (the source is a field of the definition, `dispatch.home.link`, so a sealed library copy can name another file, and declare it a plain link instead), and the member's Codex loads nothing else of your Codex home. Why a separate sign-in: Codex runs outside its own sandbox and refreshes the token it was given. Through a link to your own `~/.codex/auth.json` a member run could write your file or replace the link, and where the token rotates, the token left in your file can be revoked, which signs you out of your own Codex; two runs at once, each refreshing the one file, would race on its token, which is why the member gets a copy that cannot refresh (below). Make the members' sign-in once, in your terminal; the directory must exist before the login: `mkdir -p ~/.codex-members && chmod 700 ~/.codex-members && CODEX_HOME=~/.codex-members codex login`. A run is refused (exit 2) when that file does not exist (a link to a missing file too), is not a regular file, or resolves, by its real path, inside `~/.codex` or inside the directory your own environment names in `CODEX_HOME` (unless your `CODEX_HOME`, made absolute without following a link, is the directory the definition names for the members' file, `~/.codex-members`: a directory of the definition that is itself a link into your `CODEX_HOME` is refused, since the exemption is for the directory named, not for wherever it leads): `qargi local prepare` refuses before it makes anything and `qargi local run` before it starts anything, each naming the path as the definition declares it and that login. The same holds for the link source of any runtime, a library pack included: one that resolves into `~/.codex` or into your `CODEX_HOME` is refused by `qargi provider check`, by the seal and at `import`, as well as at prepare and run. A run checks the file again just before it copies it (and once more when it holds the lock of a plain link, below), so a file swapped for a link into your own sign-in is refused (exit 2) and nothing is copied; the copy is read once, from one open file, and the run has a file of its own, so a swap after that changes nothing in the run. A source another program is writing at that moment is at worst a file that does not parse, which refuses the run (exit 2) and copies nothing. Only the same user can write the members' directory, so keep it so. The result of the check of a definition (`qargi provider check`, the seal) depends on your environment and your file system: it changes with your `CODEX_HOME` and with where the links of your home lead. If your own `CODEX_HOME` is `~/.codex-members`, your Codex shares the members' sign-in, and its token refreshes change the file the runs copy; use another directory for your own Codex. **A private copy, not a link.** Codex refreshes the sign-in it is given in place, and two runs refreshing one file race on its token, so the runs that shared the members' sign-in used to run one at a time. The definition now declares its link private (`dispatch.home.link[].private`): each run reads the members' file once and writes a copy of its own, `RUN/home/.codex/auth.json` (a regular file, mode 600, made exclusively, never a link), in which `tokens.refresh_token` is the placeholder `qargi-no-refresh` and the rest is as it was. A copy with no real refresh token cannot refresh and cannot race, for as long as its access token lives: the runs that share the file take no lock and overlap, so a build and a review on `codex` run together and no second run prints a wait. Seen with `codex-cli` 0.172.0, in one probe each: Codex refuses an auth file with no `refresh_token` key but accepts the placeholder; with `last_refresh` twelve days old and the placeholder, a tiny `codex exec` still completed and left the real file unchanged, so the runtime does not refresh on the age of the sign-in alone. One probe is not a guarantee: a version that refreshes anyway would write the copy, never the real file. The access token in the copy is the real one, so a member still holds a live access token in its own home, as the link gave it: the read barrier stays `partial` and nothing about it changes, but the refresh token no longer reaches the member. A run that would outlive the access token is refused before it starts: the run's own bound (`timeout_s` of the definition, 3600 s, or `--timeout`) plus a margin (900 s, `private.expiry.margin_seconds` of the definition) must be less than the seconds the token has left (read from its `exp` claim without checking a signature, never printed or recorded), else the refusal `runtime-signin-expiring` (exit 1, no attempt used, no `--again` needed) names the declared path, the seconds left, the bound and where it is set, the margin, whether the bound alone is longer than the time left (then lower `--timeout`: a new sign-in lasts only as long as Codex gives one) and the login to run, `CODEX_HOME=~/.codex-members codex login`; it is checked again after a wait for a plain link's lock. **The real sign-in is refreshed by the run that needs it.** The definition declares `private.refresh`: the read-only `codex exec` (a one-word prompt, the default model, `--skip-git-repo-check`, a scratch directory as its working directory, timeout 120 s, the token must then have at least 1800 s left, or the run's need if that is more, not the sum). When a copy's token would not last the run (the bound plus the margin) the runner takes the lock beside the members' file (`~/.codex-members/.qargi-run.lock`, the one a plain link uses, so only one run refreshes at a time and the runs that overlap never do), reads the file again (a run that waited finds it refreshed by the one before and goes on, and prints nothing), and otherwise runs that command once with `CODEX_HOME` naming `~/.codex-members`, so the runtime itself refreshes the real file in place; its output is discarded and never printed (it can carry tokens), it gets the scrubbed environment a member gets, and it is stopped when it outlives its timeout or when the runner is signalled. The run prints one line, `qargi: refreshing the sign-in of codex (expires in N s)`, reads the file again, lets the lock go and goes on with its copy; `RUN/dispatch.json` records `home.private[].refreshed` (`true` or `false`, nothing else). A command that fails, times out, leaves the file as it was, or leaves a token that still does not last is the refusal `runtime-signin-expiring` with the cause `refresh-failed`, naming `CODEX_HOME=~/.codex-members codex login` as before, with no second try; the members' file is never restored (a runtime that rewrote it keeps what it wrote). `--dry-run` prints `HOME_REFRESH=` (what it would run) and refreshes nothing, and `qargi local prepare` never reads the sign-in. This is the one place the runner itself starts the runtime, apart from a member: the command is the definition's own, its first word must be the definition's command (`qargi provider check` and the run both refuse another). **Not verified against the real runtime:** no probe has seen `codex exec` refresh an expiring token (the probes above show only that the placeholder is accepted and that the age of the sign-in alone does not make Codex refresh it); a refresh that does not extend the token fails closed as `refresh-failed`, and you sign in with the login as before. A source that is not a JSON object, lacks `tokens`, or holds no access token with an expiry is refused (exit 2), naming the declared path. Nothing is written back to the members' file, by qargi or by what the member does to its copy; a note names a copy that was changed or removed, never a value. The copy is removed when the run ends, also after a failure of the runner and a signal; a runner killed with SIGKILL cannot, so `qargi local list` and `verify` name the copy it left (a private copy of a sign-in that a start of qargi local run left), `qargi local run RUN --again` replaces it and `qargi local clean` removes it with the run. A definition whose link is plain (a sealed library copy that does not declare `private`) keeps the old rules: the runs that share the file run one at a time, by an exclusive lock on `.qargi-run.lock` in the directory of the file; a second run prints `qargi: note: another codex member run holds the lock ~/.codex-members/.qargi-run.lock (one run at a time per sign-in); waiting for it to end` and waits (SIGINT or SIGTERM ends the wait), after a second line that names the holder from the lane record beside the lock (`qargi: note: holder is lead L, run SLUG, holding it for 14m`, and `; you are number 2 of 3 waiting` when several wait, the order they start in, since only the first waiter polls the lock and a run that finds others waiting queues behind them; a record is advisory, the lock is the authority). `--wait SECONDS` bounds the wait for that lock and for the lock a refresh of the private sign-in takes (the same file), as long as the run is not yet recorded (a refresh that is needed only after that, because the token ran short while the run waited, waits for its lock without a bound): at the bound the run is refused as `lane-busy` (exit 1) before its attempt is recorded and before anything is made, naming the holder and the wait, so the same run starts with a plain `qargi local run RUN` once the lane is free; `--wait 0` refuses at once, and without `--wait` the wait has no bound, as before. `qargi local list --lanes` shows each lane (RUNTIME, LOCK, STATE, HOLDER) and the runs waiting for it, from `/proc/locks` (the lock is found by its device and inode number) and the records, taking no lock; where the device that `/proc/locks` names cannot be compared with the one `stat` names (btrfs, an overlay), the state is `unknown (device not comparable)`, never `held`, and the holder is named only from a record whose runner or member is alive. The member holds the lock descriptor too, so a runner killed with SIGKILL leaves the lane held until the member's process group has ended (the record then says `member alive, runner gone`), and a lock file removed or replaced while a run waited is noticed: the run closes the file it held, says so, and takes the one that is there; a process of the member that moved to a process group of its own and still holds the descriptor keeps the lane busy after the runner has gone, which is the safe direction. A definition with both a private and a plain link takes the lock for the plain one. `qargi local run --dry-run` prints the file each private copy is made from (`HOME_COPIES=auth.json<-PATH`, the path only; a plain link prints `HOME_LINKS=auth.json<-PATH`), and `RUN/dispatch.json` records `home.private` (the name, the paths set, the seconds left when the run started, whether the run refreshed the real sign-in, and the sha256 of the copy as written, which lets `qargi local list` and `verify` find a copy that was renamed inside the run home; no value). This is configuration separation, not secrecy from the member: the sandbox holds writes, not reads, so the member can read the members' file by its path, and your own `~/.codex` (sessions, history, `auth.json`) by path.
- **A sign-in changed during a run.** The member's sign-in is a private copy (above): what the runtime or the member writes to it, in place or by replacing the file, stays in the run home and is removed with it, with a note that names the copy, and the members' file is never written; there is nothing to reconcile, and a refreshed token of a member's copy is lost on purpose (the real sign-in is refreshed by the run's own locked refresh, above, or by your login). The rest of this item is for a plain link, as a sealed library copy of the definition may declare. Written through the link, it lands in the members' `~/.codex-members/auth.json` directly: qargi cannot prevent a write through the link, and the run notes that the file changed; your own `~/.codex/auth.json` is not touched. Written by replacing the link with a new file (an atomic replace), it never reaches the members' file: qargi does not write it, since a sign-in of yours may have written it meanwhile and nothing qargi can check before a rename keeps such a writer out. The new file is kept in the run home as `auth.json.from-run` (mode 600, over one an earlier run kept there), named in a `HOME_RESIDUE=` line, in `home.residue` of `RUN/dispatch.json` (the name, never a value) and by `qargi local list` and `verify`, with a note that says whether the members' file is unchanged since the run started. To reconcile it: if `CODEX_HOME=~/.codex-members codex login status` in your terminal still finds the members signed in, keep that file and let `qargi local clean` remove the copy; if not, and the note says the file is unchanged, move the copy over it yourself (`mv RUN/home/.codex/auth.json.from-run ~/.codex-members/auth.json`), or sign in again with `CODEX_HOME=~/.codex-members codex login`. When the note says the file changed, keep it.

## Skills and MCP tools of a member

A Codex member receives the contract and the task. Default-off managed delivery makes no skills directory in its private `CODEX_HOME`. Untracked links in the lead's checkout do not enter its clone, and its `HOME` excludes default discovery from the lead's user directories. Committed checkout skills can still load independently, including management prose; readable files remain accessible under the runtime's contract. With the owner's opt-in, only canonical links reaching the actual role select the managed snapshot; role-specific lead links stay out. Neither skill names nor prose grant tool or execution authority. The baseline keeps bundled skills off. Tests of these delivery mechanics do not qualify actual client loading or every discovery layout.

Its MCP tools are the `[mcp_servers.PACK]` tables of the run's file for its role and class: `enabled_tools` holds the tools as the server names them (`platform.list_items`, `repo/push`, `issue-close`), and the names the model is given are the `mcp__SERVER__TOOL` form, with every character other than a letter, a digit, `_` and `-` written as `_` (`mcp__kb__platform_list_items`). Two tools whose names come out alike (`a.b` and `a_b`) are given to no one; a tool the server lists but the pack does not declare is never enabled; an `always_ask` tool is never enabled (nobody answers); a read-only role gets the declared reads only. A server runs outside the sandbox, so `enabled_tools` is what holds it. An authenticated server gets only its `url` and `enabled_tools`: a tool pack's `vault_ids` are credentials of the cloud vault, which a local run never reads, and qargi writes no bearer token, header or `bearer_token_env_var`, so a server that needs a credential fails to connect in a member run. The model-visible names were not seen offline (a server must answer); they are among the live checks.

## The output of a run

- **The report.** Codex writes the member's last message (`-o`) to a new private file of the run; when the run ends qargi checks it and publishes it as `OUT/report.md`. With `--again` the earlier report is set aside as `OUT/report.md.previous` before the member starts: a run that publishes a report replaces it, and a run that publishes none leaves it there, where no check takes it for this run's.
- **A read-only run** cannot write OUT, so the lead writes `OUT/manifest.json` beside the report: the minimal report-only manifest, with what the lead recorded of the run and no test result and no verdict; `qargi review check` still reads the Findings and the verdict line of the report.
- **A write run** commits in its clone and collects its patches into OUT; a change to a tracked file left uncommitted with no patches is a refusal (`refused`, exit 2), never a finished task. A new file the member never added is not a refusal: it is reported (`WORKTREE=untracked`, and a warning in `qargi review check`), the run can still end `ok`, and `qargi local clean` removes it with the clone, with a warning. When such files are the task's work, send the run back to commit and collect them.
- **Usage** is tokens only, added up from the `turn.completed` events into `RUN/dispatch.json` and the `USAGE=` line; a count no event reports is named as not reported, never recorded as 0. A ChatGPT sign-in reports no money per run, and a wall-clock timeout is not a token or money ceiling.

## Codex as the lead

1. Install the Codex CLI and sign in yourself (`codex login`, in your terminal); `codex login status` tells you whether you are signed in. For the members qargi starts, sign in once more, into a directory of their own (they never use this sign-in), which you make first: `mkdir -p ~/.codex-members && chmod 700 ~/.codex-members && CODEX_HOME=~/.codex-members codex login` ([Sign-in](#what-a-member-can-reach) says why).
2. `./install.sh --user --runtime codex` links the `qargi-*` skills into `~/.codex/skills`, the user skills directory of the `codex` definition, and the `qargi` command into `~/.local/bin` (keep it on `PATH`). It leaves a Claude Code install as it is, and `./install.sh --user` later refreshes both; `./install.sh --user --uninstall --runtime codex` removes only the Codex skills. A `CODEX_HOME` of yours that is not `~/.codex` does not see them. Seen offline with the skills linked there in a scratch home (`codex debug prompt-input`): a Codex session lists all eleven lead skills. codex-cli 0.167.1 drops a skill whose front matter it cannot parse, without a word; `qargi-task` was dropped that way until its `argument-hint` was quoted, and the install test now checks the front matter of every skill with a strict rule.
3. Attach the project with its local runtime: `qargi project attach ~/src/myproject --name myproject --provider-local codex` (or `qargi project set myproject models.provider.local codex`). There is no `qargi agent add` for Codex: it keeps no member files, and every member runs through `qargi local run`.
4. Codex reads the repository's `AGENTS.md` itself; qargi adds nothing to a project's committed files. The project's packs (`qargi packs apply --target codex`) wait until the `skills` claim of `codex` is verified, so a lead session loads the user-level skills only.
5. A Codex session has no hook that qargi uses, so nothing sets `QARGI_LEAD` for it (`qargi provider notes identity`). The marshal verbs take `--as ID`; the other verbs that ask who leads (`feature`, `local`, `review`, `release`) take no `--as` and read `QARGI_LEAD`, so a lead that claims or takes a feature with `--as` alone is then refused by `qargi feature sync` and the like, as another lead. Start the session with `QARGI_LEAD` in its environment, or set it on each command (`QARGI_LEAD=ID qargi feature sync NAME`), or lead without an identity: the anonymous `user@host` works, warns, and is shared by every such session of yours on the host. Two lead sessions on one host, as there are during a handoff, therefore need an identity each: under one identity the marshal answers both `yours` and refuses neither. Not verified: that a Codex session hands its environment on to the commands it runs. Run a command that asks for input or a credential in your own terminal (`qargi provider notes commands`).

Not verified: which sandbox and approval settings a Codex lead session needs for qargi's own writes. `qargi` writes `~/.qargi`, the scratch directory of the runs and their TMP under `/dev/shm`, all outside a session's workspace, so under `workspace-write` expect Codex to ask or refuse. Installing Codex beside Claude Code is covered by `tests/test_install_runtimes.sh`, in a scratch home: both runtimes install side by side from one tool, each is removed on its own, and a link of one is left as it was by an install of the other; a real Codex and Claude Code session loading both is not verified.

**Moving the lead between Claude Code and Codex.** The lead skills of both runtimes read the same stored state (the marshal records, the runs, the project's answers), so the lead can pass from a session of one to a session of the other. The `qargi-session` skill has the procedure ([The lead moves to another runtime](../../skills/qargi-session/switch.md)):

1. The outgoing lead writes the handoff note, `qargi marshal handoff --write FILE`, and adds what is not stored, its runtime and its lead identity among it.
2. You start the incoming session in the work tree where the work continues, with the note's path as its first message.
3. The incoming lead reads the note and reports what it believes before it does anything: the state, its runtime, the identity in its `QARGI_LEAD` and where that comes from, the skills it sees. Until it is told to go on it runs only verbs that read (`qargi marshal status --all`, `qargi marshal check NAME`).
4. The report is checked against the stored state (`qargi marshal status --all`, a fresh `qargi marshal handoff` when the work moved).
5. Then each feature changes hands: the outgoing lead runs `qargi marshal release NAME --note "..."` and nothing on the feature after it, since a released feature has no lead until it is taken and the flow verbs then refuse no session. The incoming lead runs `qargi marshal take NAME` with its identity in `QARGI_LEAD`, in its environment or on the command (`QARGI_LEAD=ID qargi marshal take NAME`), never with `--as` alone. When the outgoing session ended without a release, the incoming lead claims the feature as its successor, `qargi marshal claim NAME --as-successor-of ID`, which is accepted only once the old lease is stale, on the same host, as the same OS user and in the same work tree; the runtime plays no part. Every other case is your `qargi marshal takeover`.

What does not carry over, on either runtime: no approval, plan token or word of yours transfers with a handoff; a release cut approved under one lead identity is refused under another, and each remaining step then takes its own plan and approval; a lead identity is a label, not an authority. Skills load when a session starts, so a skill that changed needs a new session.

What a Codex lead does not have: a guard hook (as for a member, above); a session-start hook, so it reads the lead's resources and the open features by running `qargi hook session-start` itself, which prints JSON; session transcripts that qargi can read, so on a project whose local runtime is `codex`, `qargi lead compact-check --advise` prints `context: unknown` and gives no advice on compacting, and on a project whose local runtime is `claude-code` it reads a transcript of that runtime, never the Codex session's (the one `QARGI_LEAD` names; a Codex lead's id names none, so it prints `context: unknown`), so a Codex lead leaves that figure and the advice drawn from it aside; and a launch line in the handoff note, whose packs section says for such a project that the runtime has no skills support. A project has one own local runtime, and may have extra ones the owner enabled: the members on `codex` start with `qargi local run` from a lead on either runtime, and the members of an in-session runtime such as `claude-code` start only from a Claude Code session, so a Codex lead cannot dispatch them. `qargi provider notes` prints the notes of the project's own local runtime, and `--runtime NAME` or `--run RUN` those of the runtime a member runs on ([Sending tasks to a second runtime](several-runtimes.md)); `qargi provider show codex --json` holds those of `codex` whatever the project uses.

Not verified: a handoff between a real Claude Code session and a real Codex session. The verbs of the procedure were run against a scratch home under two lead identities given by `QARGI_LEAD`, and once with the incoming identity given by `--as` alone: a released feature that nobody had taken refused neither identity's `qargi feature sync`, the outgoing identity was refused after the take, and the feature taken with `--as` alone refused `qargi feature sync` until `QARGI_LEAD` named the same id.

## A complete local run

A build member runs with the project's local runtime `codex` (or, in a project whose own runtime is another one, with `qargi local prepare --runtime codex` once the owner enabled it: [Sending tasks to a second runtime](several-runtimes.md)).

Prepare prints `RUN=...`, `CLONE=...`, `OUT=...` and `TASK_FILE=RUN/task.md` (the whole task block: ROLE, TASK, DONE, SCOPE and paths). The dry run shows the argv, run configuration path, tools, baseline and prompt without running anything. The run starts codex exec in the clone and prints `OUTCOME=`, `REPORT=` and `USAGE=`. Verify checks that the repository's refs are unchanged and OUT holds patches; review check checks the patches, manifest, SCOPE and DONE. Apply puts the patches on `agent/dots` with your go-ahead; clean after the work is applied and merged.

```sh
printf 'Accept a period in a user name.\n' > ~/tasks/dots.md
qargi local prepare --repo ~/src/myproject --base feature/dots --slug dots \
  --scratch ~/.cache/qargi-runs --role build --task-file ~/tasks/dots.md \
  --done "make test" --scope src --scope tests
qargi local run "$RUN" --dry-run
qargi local run "$RUN"
qargi local verify "$RUN"
qargi review check "$RUN/out"
qargi review apply "$RUN"
qargi local clean "$RUN"
```

A review member reads the change and returns a report; it needs the read-only barrier. The Codex sandbox is verified as a partial barrier ([What is verified](#what-is-verified)), so `prepare --role review` takes the role and `local run` prints the barrier's note: the member's shell writes are refused, its reads are not.

The last message becomes `OUT/report.md`; the lead writes `OUT/manifest.json`. Review check passes with the Findings and a last line `verdict: accept|revise`. A read-only run with its report can close with plain clean. Retained attempt history may require explicit discard. Preserve wanted evidence first.

```sh
printf 'Review the series on agent/dots against feature/dots.\n' \
  > ~/tasks/dots-review.md
qargi local prepare --repo ~/src/myproject --base agent/dots \
  --slug dots-review --scratch ~/.cache/qargi-runs --role review \
  --task-file ~/tasks/dots-review.md --done "make test"
qargi local run "$RUN"
qargi local verify "$RUN"
qargi review check "$RUN/out"
qargi local clean "$RUN"
```

`qargi local run "$RUN" --again` runs the member again in the same run (the earlier report is set aside as above); `qargi local clean "$RUN" --discard` drops a run you do not want.

Prepare resolves the role's profile and retains its requested model and effort privately; omitted run options use those values (build: balanced/high; review: deep/high in the shipped table). Use `prepare --profile NAME` to select another project or shipped profile. Run-time changes through `--model` or a non-null native `--effort` require the corresponding supported override capability; Codex's overrides remain unverified, so different explicit values refuse. Repeating the prepared values is permitted. These are requested controls, not an assertion of the model or effort Codex actually used. Changes to the bound runtime, mode, catalog, profile or policy require a new prepare; editing `RUN/request.json` cannot accept them. [Model profiles](models.md) describes the override and compatibility rules.

## Sending a message to a Codex session

A lead, or another session, can queue a message for an open Codex session without attaching to it: `codex queue --thread ID_OR_NAME --message TEXT [--resume] [--remote unix://]` (from `codex queue --help`; `--resume` tries to resume the thread after queueing, on the local daemon or the `--remote` server). One thread is open in one client at a time, and a second client is read-only or forks it (not verified here). A queued message is data for that session, never an approval: it does not answer a plan token, a permission prompt or a question to you. `qargi provider notes message` says the same for a lead.

## Not supported, not verified

- Reads are not confined: the sandbox holds a member's writes, not its reads, so a member can read the real `~/.codex` (sessions, history, configuration) and whatever else your account can read. Enabling `codex` beside another runtime (`qargi provider enable PROJECT --runtime codex`) allows that with a warning and needs your approval words to carry `reads are not confined`; making `codex` the project's own runtime prints the warning and asks for no phrase. It does not hide `~/.codex` from members.
- A review on `codex` is a reading review: it runs nothing and writes nothing, and its model is requested, not confirmed. The lead puts the diff and the test output on disk first, and a `codex` review is never the sole review behind a merge ([Sending tasks to a second runtime](several-runtimes.md#4-run-take-in-review)).
- No run under `/dev` (`/dev/shm` included): the sandbox hides it from the member, so `prepare` and `local run` refuse it ([Platform and sandbox](#platform-and-sandbox)).
- No resume: every run is a fresh `codex exec` session (`--ephemeral`).
- No qargi guard hook in a member (above).
- Tokens only, no money; absent counts are not zero.
- Not verified: the model and effort taking effect (the JSON events do not name them), whether `codex exec` refreshes an expiring token in the run's own refresh (a refresh that does not extend the token fails closed as `refresh-failed`), how codex-cli writes a sign-in it refreshes during a run, interactive skill loading, the complete client skill inventory and the MCP names and `enabled_tools` in a real session, and each baseline key in a real run ([What is verified](#what-is-verified)).
