# Choosing models

qargi ships one table (`lib/model-defaults.json`) with two **bases**, one per guard class, and a set of **profiles**. The bases are `worker` (roles build, write and test; write class) and `reviewer` (review; read-only): registered members for in-session runtimes, logical bases for command runtimes. A profile is not a member; it is `{base, tier, effort, purpose}`, resolved at dispatch:

| Profile | Base | Tier | Effort | Purpose |
|---|---|---|---|---|
| `build` | worker | balanced | high | changes the code |
| `write` | worker | balanced | medium | writes the documentation |
| `test` | worker | balanced | low | writes and repairs tests |
| `review` | reviewer | deep | high | judges a change, read-only |
| `auditor` | reviewer | fast | low | checks a diff or a feature in a clone of its own |
| `advisor` | reviewer | deep | high | reviews the lead's synthesized diff before sign-off |
| `researcher` | reviewer | frontier | high | research and design judgment on a hard question; opt-in only |
| `lead` | none | balanced | medium | the lead's own session; never dispatched |

A **tier** (`fast`, `balanced`, `deep`, `frontier`) is mapped by the model catalog of the runtime's family (`lib/providers/catalogs/claude.json` for `claude`) to a full model id for cloud (`claude-haiku-5-5`, `claude-sonnet-5-5`, `claude-opus-5-5`, `claude-fable-5-1`) and to an alias for local dispatch (`haiku`, `sonnet`, `opus`, `fable`); a runtime with a single model writes it once for every tier. A project picks the runtime of each surface with `models.provider.local` and `models.provider.cloud` in its answers; there is no default, so a verb that needs a surface (`agent`, `provision`, a read-only `local prepare`, a cloud session, `packs apply --target`) refuses a project that leaves it out (exit 2, naming `qargi project set PROJECT models.provider.SURFACE NAME`), and a name with no definition is refused. `qargi project attach` and `qargi project new` store them with `--provider-local` and `--provider-cloud` (or `--provider NAME` for one name), and nothing without. The `frontier` tier is an opt-in escalation: no default profile except `researcher` uses it, and `researcher` is used only when you or the lead name it for the task.

The family `openai` (catalog `lib/providers/catalogs/openai.json`, used by the local runtime `codex`) maps the tiers to model ids, passed as they are with no alias: fast `gpt-6-luna`, balanced `gpt-6.1-terra`, deep `gpt-6.1-sol`, frontier `gpt-6-astra`; the effort levels `low` to `max` keep their names, and none of the tiers is verified yet. That an id is in a catalog says it exists, not that you can use it: `codex debug models` lists the ids the CLI knows (these four among them, seen with codex-cli 0.167.1 signed out and offline), and only a run with your sign-in shows that one is available to you. The tier order is the order of the profiles (a small fast model to the largest), not a benchmark result: qargi has measured no tier against another. A project uses one runtime per surface, so the models of one project's local members come from one catalog: a project on `codex` cannot send some roles to another local runtime.

A project adds or overrides profiles in its answers as `profiles.<name>` (`base`, `tier`, `model`, `effort`, `purpose`, `abilities`, the roles it may serve). A profile whose base class conflicts with its `abilities`, or with the role being dispatched, is refused.

For command runtimes, `qargi agent models [--project P] [--json]` uses the same profile resolver as `agent for`. Each row shows the logical base, selected model ID or alias, requested effort level and source (`shipped` or `project`). Legacy `roles`/`lead` answers and registered members do not select these requests; missing member registration does not prevent command dispatch. JSON retains the existing top-level keys and profile metadata and adds `mode: "command"`, profile `selected` and `requested_effort`, and base `logical: true`. `members` is empty, base registration flags are empty, and refused profiles carry the resolver's reason in `refused`, `flags` and `warnings`. The intentional never-dispatched `lead` recommendation is informational, with `refused: null` and empty `flags`; `agent for --profile lead` still refuses it. `effort_control` describes native support; the requested level stays visible even when every native mapping is null. These are requests, not observed runtime identity. In-session member displays and cloud resolution keep their existing behavior.

Member registration and missing-alias flags apply to in-session rows. Row flags do not fail the display, but command-mode extension composition or load errors may fail `agent models` before it can display rows.

An absent or null `profiles` container uses the shipped command profiles. Non-null containers must be objects, and selected entries must follow the project profile field rules: null entries and null field values are refused. Malformed unrelated entries do not block a valid selection. Command model selection uses an alias only for a catalog reference with `use: alias` and a nonempty alias; otherwise it uses the ID, including inline models and `use: id`.

For command runtimes, `qargi local prepare` resolves an explicit `--profile` or the role's own profile, falling back to build for a write class or review for a read-only class when the role has no profile. The worker/reviewer base is logical and needs no member registration. Prepare stores the resolved profile, base, requested model/id and effort, role, class and runtime in lead-owned private lifecycle authority before publishing the run. `RUN/request.json` and `RUN/profile` are inspection mirrors. `local run RUN` uses that prepared model and effort when each option is omitted; editing RUN files never selects another request.

Explicit `local run --model` and `--effort` remain available. Model tiers, catalog aliases and IDs follow the runtime's id/alias policy; an ID matching its pattern is syntax-checked without claiming vendor access. Changing the model requires supported `per_dispatch_model_override`; changing a non-null native effort control requires supported `per_dispatch_effort_override`. Supported means verified yes or partial; unverified counts as unsupported. Repeating a prepared value needs no override capability. A null effort mapping omits the argument with a note while retaining the requested level. Empty explicit values refuse. These values describe what qargi requests, never the runtime's observed identity.

Runtime, mode, catalog, selected profile inputs, composition and effective capability/barrier policy are bound at prepare. Drift refuses before launch, including with explicit overrides: re-run `qargi local prepare` to make a new request. Dry-run changes no bytes, including on refusal. Retry retains the original private request; saved `request.json` comes from that authority and remains an evidence mirror. Existing lifecycle records without a request retain the former balanced-model/no-effort defaults and override validation; no request is backfilled from RUN or saved files. Genuinely unmarked legacy runs retain their existing inspection/cleanup paths and require reprepare for actual runtime dispatch. In-session and cloud selection are unchanged.

For an in-session runtime, `qargi agent for ROLE [--profile NAME] [--project P] [--json]` prints one line, `MEMBER MODEL EFFORT PROFILE`; MODEL is the alias, or `-` when there is none. The lead spawns the Agent tool with `subagent_type` MEMBER, `model` MODEL (omitted when `-`) and `effort` EFFORT: the call's model and effort override the member definition. `qargi local prepare ... --role R [--profile P]` resolves the profile before it clones anything, records it in `RUN/profile` and prints `PROFILE=`, `MEMBER=`, `MODEL=` and `EFFORT=` (`PROFILE=<role>` without `--profile`). Advisor sign-off uses `--profile advisor` on review, a per-task diff check `--profile auditor`, and `researcher` only when the owner or the lead names it. `qargi agent models [--project P] [--json]` shows the bases, the profiles (the project's merged over the shipped ones) and the members of that project (`--project`, else the project in effect; with neither, exit 2); an in-session member that is not a base is flagged.

Search is not a role: mapping the repository and finding call sites is done by a read-only exploration subagent on a small model inside the lead's context. The lead's own session model is chosen in its runtime (in Claude Code `/model` or settings, in Codex `codex -m MODEL` or its configuration), not by qargi; the `lead` profile is the recommendation and the cloud lead's default `lead.model`.

Cloud: the four role agents (`<project>-build`, `-write`, `-review`, `-test`) keep working with explicit model ids from the runtime's catalog and the project's answers (`roles.<role>.model` and `effort`). A project can also provision the two bases, `<project>-worker` and `<project>-reviewer`, and start a session of a role and profile on one with `qargi start|send <project>-worker --role build --profile build --asked ...`: the model and effort are overridden for that session (always as a full model object), the role's prompt is rendered for it, and the tools stay those of the base. `qargi agent for ROLE --surface cloud --project P` prints the base it would use; it exits 1 when the base is not registered and 2 when the provider's cloud override capabilities are not verified (a role agent is never chosen for you: start a session on it by its name). A reviewer base needs the project's `qargi provider accept NAME --surface cloud --no-barrier --asked ...` first, because the cloud has no read-only barrier.
