# Providers and runtimes

A **runtime** is one way of running agents on one surface (local or cloud), and it is data: a JSON definition (`lib/providers/schema-2.json`) with the models of each tier and the date and source each was verified on, the effort levels it understands, a capability matrix (model and effort overrides at dispatch, a fixed tool list per agent, a read-only barrier, a session budget ceiling, memory stores, skills, MCP), where its skills, agents, MCP file, settings and memory live and how each is linked into a work tree (a directory link, one link per entry, a copy), how a member is written as the runtime's own file, how a member is dispatched, and how a read-only member is held. A **family** groups the runtimes that share a **model catalog**. Claude ships as the family `claude` with the catalog `claude` and two runtimes, `claude-code` (local) and `claude-platform` (cloud). Three kinds of pack share the provider library, `~/.qargi/config/packs/providers/NAME/`: `provider` (a runtime), `catalog` and `extension` (capabilities a project adds to a runtime). `qargi provider list`, `show NAME` and `check NAME` print them, the matrix and what degrades; a project picks one runtime per surface with `models.provider.local` and `models.provider.cloud`, and there is no default.

Add a runtime with no code: `qargi provider new NAME`, edit the definition ([CONTRIBUTING](../../CONTRIBUTING.md#add-a-runtime-with-no-code) has a worked example), `provider check NAME`, `provider seal NAME`, then `qargi project set P models.provider.local NAME`. A command-line runtime is dispatched by `qargi local run RUN` (`--dry-run` prints the argv, the working directory and the prompt): the argv is an array in the definition, never a shell string, and only the environment variables it names reach the process. Its command word is resolved on your `PATH`, entry by entry, to the first regular executable file whose real path has that name (or the name with an extension, such as a launcher `NAME.js`, or with a suffix after a dash, such as a release binary `NAME-x86_64-unknown-linux-musl`), and that path runs: the dry run prints it (`COMMAND=`) and `RUN/dispatch.json` records it (`command`). A wrapper or shim that is a link to a program of another name, as a version manager installs, is passed over with a note, because under the run's home it would look for the tool there; when nothing else is left the run is refused (exit 3), naming each entry and why. A shim that is a script of the command's own name cannot be told apart and runs as found. The member's own `PATH` is yours, unchanged, wrappers for other tools included, and those run under the run's home too ([Codex as lead and as member](codex.md#platform-and-sandbox) says what follows). A runtime that keeps its settings and sign-in in a directory of its own declares `dispatch.home`: the member gets that directory under the run's home, in the variable the runtime reads, and the files it lists from your home (a sign-in file, never qargi's own files or your ssh, gpg, git, forge or cloud credentials) are linked into it when the run starts and unlinked when it ends. The file is never copied and the dry run names the link only (`HOME_LINKS=`); the member can still read it through the link. A runtime that holds the MCP tools of a server in the server's entry (`resources.mcp.tool_lists`) can declare `dispatch.run_config`: each run then gets its own configuration file, in the run home (`in: home`, for a runtime that reads its configuration from there) or in `RUN/config` (`in: run`, passed with `{run_config}` in the argv), listing the tools a member may call for the run's role and class (never an `always_ask` tool, under the read-only class only a declared read; the role is the one the lead's registry records). A definition can also give the file a `baseline`, settings of the runtime's own configuration written into every run's file whatever tools reach the role, so a run with no MCP server and a run with one get the same settings; without a baseline a run whose role no tool pack reaches gets no file. The dry run prints the file's path, the tool names and the baseline (`RUN_CONFIG=`, `RUN_CONFIG_TOOLS=`, `RUN_CONFIG_BASELINE=`), never the servers' addresses. For `codex` it is `CODEX_HOME/config.toml` in the run home, the user-level configuration of the member's Codex; it is not all a member's Codex reads ([Codex as lead and as member](codex.md) has what loads and what does not). A runtime whose sandbox hides part of the filesystem from the member declares `dispatch.hidden_paths`: the path `prefixes` it hides, per class the run paths it `shown` anyway (the places it binds in, such as a write class's writable directories) and a `note` saying why. A read-only member works with its clone, its contract and its git wrapper, a write member also with OUT and TMP (the task block reaches it in the prompt); when one of those that its class does not show lies under a prefix, by its path or its real path, `qargi local prepare` refuses the run before it makes anything and `qargi local run` before it starts anything (exit 2), naming the path, the prefix and the fix (`--scratch` on another filesystem, or `QARGI_RUN_TMP`). `codex` declares `/dev`, so a run whose scratch directory is under `/dev/shm` is refused for it; use a directory on disk. A runtime that writes the member's last message to a file it is given names `{final_message}` in its argv: a file in a directory of the run made new for each run, never a file of OUT. When the run ends qargi takes it only as a regular file with one name, of text, at most 1 MiB (a link, a pipe, a directory or a second name of another file is not followed, read or published), publishes it as `OUT/report.md` by renaming a new file over that name, and prints `REPORT=` (and records `report` in `RUN/dispatch.json`). On `--again` the report of the earlier run is set aside as `OUT/report.md.previous` before the member starts: a run that publishes a report replaces it (`PREVIOUS_REPORT=replaced`), and a run that publishes none, a failed one for instance, leaves it there (`PREVIOUS_REPORT=kept`), where no check takes it for this run's report. A `report.md` that is not a plain file of its own refuses the run before anything starts. A read-only member may write nothing, so for a read-only run with such a file the lead also writes `OUT/manifest.json`: the minimal report-only manifest that `qargi review save` writes (status, base, no commits, the report in `artifacts`) with what the lead recorded of the run under `run` (its id, role, runtime, class, the model and effort qargi passed, start, seconds, exit and outcome), taken from the lead's registry and `RUN/refs.before`, never from the member. It is written only when the outcome is ok, the report was published and OUT holds no patch (`MANIFEST=`, or `MANIFEST=none: WHY`), and it claims no test and no verdict: `qargi review check` still reads the Findings and the verdict line of the report, and refuses a report without them as before. The run then goes through `qargi local verify`, `qargi review check` and `qargi local clean` like any review run, with no `review save`. The model and effort it names are what qargi passed, not what the runtime confirmed. `provider import SOURCE` takes someone else's pack from a directory, a JSON file or an https git URL. Every change to the library (`new`, `import`, `seal`, `remove`, `enable`, `disable`, `attest`) is a plan, a token and your approval, and a pack with executables also needs `--approve-exec` naming every one. A pack holds text only: scripts you can read, never a compiled program, an archive or a symlink; secrets are refused, opaque blobs and scripts that fetch and run code are flagged, and a vendor CLI is installed by you and only named. An approved executable is code that runs with your rights; the guard does not contain it, so read it before you approve it.

`provider new` drafts a pack in the library, `~/.qargi/config/packs/providers/NAME/`, unsealed (`provider import` stores one sealed). The guard reads every definition there, sealed or not, to learn which skills and agents directories the runtimes name, and it fails closed: while one definition does not load (not valid JSON, a name that clashes with another or disagrees with its directory), every call of a member that writes, or reads a protected place, is refused, with a message naming the pack, until you fix it (`qargi provider check NAME`) or remove it; a call that needs no such directories (`ls`, `git status`) still runs. Edit a draft that may be broken for a while in a scratch directory outside the library and bring it in with `provider import DIRECTORY` when it is whole.

A capability counts only when the definition claims it and it is verified. A shipped definition carries a `verified_on` date for each; a library definition is verified by `provider check` (the hermetic cases: the agent render, the skills link, the read-only corpus through the guard, an adapter's stub), which records it bound to the definition's hash, so an edit or a reseal makes it stale. What no hermetic case can show (an operating-system sandbox that really holds, a real model id) is recorded with `qargi provider attest NAME CAPABILITY`, which runs and spends nothing itself and is asked each time, with the command, the scratch resources, the smallest model, the ceiling and the expected cost stated first. An extension is enabled for one project with `provider enable PROJECT EXTENSION`; two extensions that add the same thing are refused, and what one provides counts only after its own check.

The rules that do not depend on the runtime: a surface whose read-only barrier is not supported cannot serve the review role, unless you accept that for the project with `qargi provider accept NAME --surface S --no-barrier --asked "..."` (it prints a plan and a token, records `models.accept_no_barrier` and writes the audit log); a runtime with no effort control has the effort dropped and `qargi agent models` says so; a runtime without a per-dispatch model override runs the base with its own model, and a profile with another model is refused; and the output of a read-only run is never applied as patches. For `claude-code` the local barrier is the guard hook (partial: shell writes are caught heuristically and `local verify` is the backstop); the cloud review agents of `claude-platform` have no barrier, so a cloud review role needs your acceptance before it is provisioned or started. A runtime that is not a hook runtime holds a read-only member another way (the runtime's own sandbox flags, or an adapter) or not at all, and what qargi does for any runtime is the same: a git wrapper without credentials, so an ordinary push has nothing to authenticate with; patches checked by `qargi local verify` and `qargi review check` and reviewed before they are applied; and the class recorded by qargi and not by the task text.

The local runtime `codex` (family `openai`, data only) is held and wired as follows; [Codex as lead and as member](codex.md) has the details, a Codex lead's setup and a complete run. Three of its claims are verified by live checks with codex-cli 0.167.1 on 2026-11-11 and dated in its definition: headless dispatch (a write-class run end to end), the read-only barrier (partial: the sandbox refused a shell write offline and in a live read-only member) and the token report, so a review role runs on it with the barrier's note and needs no `provider accept`. The model and effort overrides (accepted in a run, but no event names them), skills and MCP stay unverified and count as not supported.

| Part | `codex` |
|---|---|
| Dispatch | `qargi local run` starts `codex exec` in the run's clone with the prompt on standard input; Codex writes the member's last message to a new file of the run (`-o {final_message}`), which qargi checks and publishes as `OUT/report.md` |
| Review output | the report is the member's last message; the lead writes the run's `manifest.json` beside it from its own record, so a read-only run passes `qargi review check` with no `review save` |
| Read-only barrier | the Codex sandbox, `--sandbox read-only` (a write run gets `workspace-write` with OUT and the clone's `.git` added), verified `partial` (codex-cli 0.167.1, 2026-11-11): it holds the member's shell commands, not its reads, and not a hosted tool or an MCP server. qargi runs on Linux only, where codex-cli's sandbox is bubblewrap (`codex sandbox`: a read-only root, seccomp, no network); Codex's macOS sandbox plays no part |
| Configuration | the run's `config.toml` in its `CODEX_HOME` always carries the definition's baseline: `approval_policy` `never`, no shell network, no `/tmp` (the run's `TMPDIR` stays writable), hosted web search, apps, plugins, hooks and the bundled skills off; `--ignore-rules` drops every rules file and `--strict-config` refuses an unknown key. Your Codex configuration is not loaded (`CODEX_HOME` and `HOME` are the run home), nor the clone's `.codex/` (a run clone is never trusted), while the clone's `AGENTS.md` is; a system-wide or managed Codex configuration is not excluded. Each key is read by codex-cli 0.167.1 (seen offline); that each holds in a real run is not yet verified |
| Skills | none of qargi's: a member receives the contract and the task; only skills the repository commits under `.agents/skills` load |
| Commits | a write member commits in its clone and returns patches: `workspace-write` keeps `.git` read-only, so the clone's `.git` is added as a writable directory (`--add-dir {clone}/.git`, seen to let `git add` and `git commit` work with codex-cli 0.167.1). The cost: the member can change its own clone's git configuration and hooks, and a hook, `core.fsmonitor`, an alias or a filter driver set there runs as you when you run git in that clone. `qargi local run` reads the clone's `.git/config`, `hooks/` and `info/` before the member starts and compares them when it ends, for every run whose argv grants the clone's `.git` and every run whose class has no sandbox arguments: a change other than what `git branch` sets (`branch.NAME.remote` and the like) is named in a `GITDIR=changed:` line and in `git_dir` of `RUN/dispatch.json`, by key and entry, never a value; nothing is restored. Never run git in a write member's clone: take the work from the patches in OUT, copy files out, or make a clean copy first with `git clone --no-local`, as git(1) advises under SECURITY. The clone's only remote is the run's bare copy with its push URL disabled, the sandbox has no network, you take the work from the patches in OUT, and `qargi local verify` compares the real repository's refs. A read-only run never gets it, and a `.git` that is a link refuses the run. A run that leaves a change to a tracked file uncommitted and returns no patches is a refusal: `qargi local run` ends it `refused` (`WORKTREE=uncommitted`) and `qargi review check` fails it unless the manifest says `BLOCKED`. New files never added are reported (`WORKTREE=untracked`, a warning in review check), not refused, and `qargi local clean` warns when it removes them with the clone |
| Guard hook | not wired: no `qargi __guard` runs, so the publish and skill verbs are held only by the sandbox's write and network denial, the credential-free git wrapper and the checks of what comes back |
| MCP | each run's own `config.toml` in its `CODEX_HOME` lists, per server, the tools the run's role and class may call (`enabled_tools`, the server's own names; the model sees them as `mcp__SERVER__TOOL`); a server runs outside the sandbox and the shell's network denial does not hold it, so that list is what holds it. An authenticated server gets only its `url`: no vault value, bearer token or token variable is written, so it fails to connect in a member run |
| Sign-in | your `~/.codex/auth.json`, linked into the run home for the run only; the member's Codex loads nothing else of your Codex home (its settings, sessions and hook trust). This is configuration separation, not secrecy: the sandbox holds writes, not reads, so the member can still read that file through the link and the rest of your `~/.codex` (sessions, history) by path. A sign-in Codex refreshes during the run is not lost, and qargi never writes your file: written through the link, it lands in your file directly (qargi cannot prevent that; a note says your file changed); written by replacing the link with a new file, it is kept as `auth.json.from-run` (mode 600) in the run home, named in a `HOME_RESIDUE=` line and in `home.residue` of `RUN/dispatch.json`, with a note that says whether your file is unchanged since the run started (compared by a hash kept in memory, never printed), and you reconcile it yourself ([codex.md](codex.md#what-a-member-can-reach)). Which way codex-cli writes is not verified yet. Only a file store is linked: Codex can keep its sign-in in the system keyring instead (a `cli_auth_credentials_store` setting, seen in codex-cli and not verified), and then there is no `~/.codex/auth.json`, the run notes that it starts without it, and `codex login status` in your own terminal tells you whether you are signed in. A `CODEX_HOME` of yours that is another directory is a note: the run links `~/.codex/auth.json` only |
| Ending a run | the link goes when the run ends, also when it fails, times out, cannot start, or the runner gets SIGINT, SIGTERM or SIGHUP. On normal exit as well as interruption, the original process group gets TERM and is watched for up to 5 seconds, then KILL for what is left. Cleanup precedes removal of the link and inspection of output. Survivors are counted, and a successful run with survivors fails. A process that moved to another process group is not contained. SIGKILL of the runner leaves `RUN/dispatch.json` saying `running`; `qargi local list` and `qargi local verify` name the link, the next start refuses while the member still runs and otherwise needs `--again`, and `qargi local clean` removes the run with it |
| Cost | tokens only (verified in live runs, codex-cli 0.167.1, 2026-11-11), added up from the `turn.completed` events; a count no event reports is named as not reported, never recorded as 0; a ChatGPT sign-in reports no money per run |
| Resume | none: every run is a fresh `codex exec --ephemeral` session |
| Mixed runtimes | not supported: a project has one local runtime, so a project on `codex` runs every member with `qargi local run` |

Unexpected runner errors preserve the start time, runner and member identity, planned home link names, refreshed file residue and cleanup notes in `dispatch.json`; credential contents and exception text are never copied into that error record. `group_left` is null when survivors could not be counted, and absent when no member started. `local list` and `local verify` still show retained links and `.from-run` files. A retry checks the original group even when the outcome is `refused`: known survivors or an unknown group state block `--again` until quiescence can be established. This check sends no signal to a recorded PID, whose identity may have changed. Processes that leave the original group and generalized recycled-PID cleanup remain outside this guarantee.

Run permissions use the lead registry's exact decoded JSON class, `write` or `read-only`; Unicode escapes that decode exactly to either string work, while trailing newlines, NULs, whitespace, other labels and nonstrings refuse. A member's class file supplies no fallback. Ordinary clean, verify, apply, run and report preserve a run with an unknown class. Explicit `qargi local clean RUN --discard` can recover a known registered legacy run without a class, whether its directory exists or is gone; it intentionally drops the run's evidence and saved output, subject to the other discard protections, including a live apply lock and refusal to remove a linked run directory. An unregistered run cannot be discarded by qargi. Deliberate discard closes the known record so compact-check can recover. Inside a member (`QARGI_MEMBER_RUN`, with HOME under the run), `qargi review check OUT` checks the output's structure without requiring or borrowing lead registry state and without running lead inspection or scrub, writing verification, or making trusted scrub marks or cache. The lead must still check it with strict registry class validation and the declared scrub.

Inspection supports plain prepared clones with default files ref storage, repository format 0 or 1, SHA-1 or SHA-256 objects, and no Git extensions beyond `objectFormat`, only within the bounds below. Trusted run ancestors are canonicalized, so an owner-controlled ancestor link is allowed; clone and `.git` must be plain directories. Git reads a private metadata copy under the lead's trusted state directory, outside clone and OUT, with a newly written minimal config. The inspection Git is an absolute executable resolved once from the lead's clean controlled PATH; a member's later PATH cannot choose it. System and global configuration and inherited Git environment are scrubbed; `GIT_NO_REPLACE_OBJECTS=1` keeps replacement refs from changing original commit counts or status semantics. The source config is parsed from a private file without following includes; only the object format and closed values of `core.filemode`, `ignorecase`, `symlinks`, `autocrlf` and `eol` are retained. Valueless booleans stay true and explicit empty booleans stay false, as Git defines them. SHA-1 uses a format-0 minimal config without an unnecessary extension; SHA-256 explicitly uses format 1 and `objectFormat`. This was tested on the current Linux Git, not on old Git or native macOS/Windows. Member hooks, fsmonitor, filters, transport, pager, editor and other configured helpers never run during inspection, including when an unknown filter is inserted after preflight. The copied index keeps its source timestamp so same-length changes within a filesystem clock tick remain detectable.

Metadata reads use directory descriptors without following links: copied files must be regular and copied directories plain. Inspection refuses gitfiles, commondir, worktree configuration, config includes, unsupported extensions or ref storage, reftable, `info/grafts`, shallow metadata, `sharedindex.*`, and object alternates (`objects/info/alternates` and `http-alternates`), including linked or special entries at those paths. Hooks and info attributes are not copied. The entire object store and refs, HEAD, config, index and packed refs are copied, bounded by a total of 512 MiB of regular-file bytes, 100,000 traversal/read steps (directory enumeration, copied nodes and each block read of up to 1 MiB), 64 directory levels below each selected top-level entry and a 60-second traversal budget. Config is limited to 1 MiB, and each Git subprocess to 60 seconds. These fixed 0.2.13 limits apply to ordinary prepared clones too; they cannot be raised by config. Sanitized reasons distinguish bounds, unsupported metadata, unreadable storage and Git failures in run, verify, review check and clean; no arbitrary config contents, exception secrets or Git stderr are included. Failure stays unknown. Ordinary clean preserves all artifacts before any removal if either commit or worktree inspection is unknown. Explicit discard remains deliberate recovery: first copy patches, reports, wanted files and `.from-run` residue out, since it removes run, TMP and saved evidence. Making a clean copy does not by itself bring an oversized object store within bounds. A copy can combine concurrent states and does not contain escaped sessions; SIGKILL can leave a private inspection directory, and no stale-directory sweeper is included. Unexpected exceptions after member start also stop the original process group before removing sign-in links; the original exception is preserved if stopping or unlinking also fails. The dispatch record keeps the survivor count, or null when it cannot be determined, and never claims an unknown group stopped.

Explicit discard of a registered run without a valid class still compares the authoritative repository refs and reports their actual unchanged or changed verdict before continuing deliberately. This internal refs-only observation grants no class permission, writes no verification mark and saves no accepted output. Ordinary verify still refuses an unknown class. Preserve or copy wanted legacy work before destructive discard; changing the member's class file does not make it authoritative.

A runtime's adapter (`lib/providers/NAME/adapter`, or a file of the pack) is optional code behind a small JSON contract (`lib/providers/adapter-schema.json`: resolve, dispatch-local, barrier-check, provision, start-session, status, collect, stop, cost; exit 3 for what the definition says is unsupported), and `bash tests/conformance.sh NAME` runs the conformance cases against it, including a corpus of calls a read-only barrier must allow or deny. The `claude-code` adapter has the local verbs, the `claude-platform` adapter the cloud start-session request builder; its other cloud verbs still run through the existing scripts. A data-only runtime has none; for a command runtime such as `codex` the same command has `qargi local run` start the runtime's stub in place of its command and checks the argv of each class, the prompt, the transcript and its usage, and the member's environment and run home.
