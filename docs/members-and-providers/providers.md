# Providers and runtimes

A **runtime** is one way of running agents on one surface (local or cloud), and it is data: a JSON definition (`lib/providers/schema-2.json`) with the models of each tier and the date and source each was verified on, the effort levels it understands, a capability matrix (model and effort overrides at dispatch, a fixed tool list per agent, a read-only barrier, a session budget ceiling, memory stores, skills, MCP), where its skills, agents, MCP file, settings and memory live and how each is linked into a work tree (a directory link, one link per entry, a copy), how a member is written as the runtime's own file, how a member is dispatched, and how a read-only member is held. A **family** groups the runtimes that share a **model catalog**. Claude ships as the family `claude` with the catalog `claude` and two runtimes, `claude-code` (local) and `claude-platform` (cloud). Three kinds of pack share the provider library, `~/.qargi/config/packs/providers/NAME/`: `provider` (a runtime), `catalog` and `extension` (capabilities a project adds to a runtime). `qargi provider list`, `show NAME` and `check NAME` print them, the matrix and what degrades; a project picks one runtime per surface with `models.provider.local` and `models.provider.cloud`, and there is no default.

Add a runtime with no code: `qargi provider new NAME`, edit the definition ([CONTRIBUTING](../../CONTRIBUTING.md#add-a-runtime-with-no-code) has a worked example), `provider check NAME`, `provider seal NAME`, then `qargi project set P models.provider.local NAME`. A command-line runtime is dispatched by `qargi local run RUN` (`--dry-run` prints the argv, the working directory and the prompt): the argv is an array in the definition, never a shell string, and only the environment variables it names reach the process. A runtime that keeps its settings and sign-in in a directory of its own declares `dispatch.home`: the member gets that directory under the run's home, in the variable the runtime reads, and the files it lists from your home (a sign-in file, never qargi's own files or your ssh, gpg, git, forge or cloud credentials) are linked into it when the run starts and unlinked when it ends. The file is never copied and the dry run names the link only (`HOME_LINKS=`); the member can still read it through the link. A runtime that holds the MCP tools of a server in the server's entry (`resources.mcp.tool_lists`) can declare `dispatch.run_config`: each run then gets its own MCP file, in the run home (`in: home`, for a runtime that reads its configuration from there) or in `RUN/config` (`in: run`, passed with `{run_config}` in the argv), listing the tools a member may call for the run's role and class (never an `always_ask` tool, under the read-only class only a declared read; the role is the one the lead's registry records). A run whose role no tool pack reaches gets no file, and the dry run prints the file's path and the tool names (`RUN_CONFIG=`, `RUN_CONFIG_TOOLS=`), never the servers' addresses. For `codex` it is `CODEX_HOME/config.toml` in the run home, the one configuration file a member's Codex reads. A runtime that writes the member's last message to a file it is given names `{final_message}` in its argv: a file in a directory of the run made new for each run, never a file of OUT. When the run ends qargi takes it only as a regular file with one name, of text, at most 1 MiB (a link, a pipe, a directory or a second name of another file is not followed, read or published), publishes it as `OUT/report.md` by renaming a new file over that name, and prints `REPORT=` (and records `report` in `RUN/dispatch.json`). On `--again` the report of the earlier run is set aside as `OUT/report.md.previous` before the member starts: a run that publishes a report replaces it (`PREVIOUS_REPORT=replaced`), and a run that publishes none, a failed one for instance, leaves it there (`PREVIOUS_REPORT=kept`), where no check takes it for this run's report. A `report.md` that is not a plain file of its own refuses the run before anything starts. A read-only member may write nothing, so for a read-only run with such a file the lead also writes `OUT/manifest.json`: the minimal report-only manifest that `qargi review save` writes (status, base, no commits, the report in `artifacts`) with what the lead recorded of the run under `run` (its id, role, runtime, class, the model and effort qargi passed, start, seconds, exit and outcome), taken from the lead's registry and `RUN/refs.before`, never from the member. It is written only when the outcome is ok, the report was published and OUT holds no patch (`MANIFEST=`, or `MANIFEST=none: WHY`), and it claims no test and no verdict: `qargi review check` still reads the Findings and the verdict line of the report, and refuses a report without them as before. The run then goes through `qargi local verify`, `qargi review check` and `qargi local clean` like any review run, with no `review save`. The model and effort it names are what qargi passed, not what the runtime confirmed. `provider import SOURCE` takes someone else's pack from a directory, a JSON file or an https git URL. Every change to the library (`new`, `import`, `seal`, `remove`, `enable`, `disable`, `attest`) is a plan, a token and your approval, and a pack with executables also needs `--approve-exec` naming every one. A pack holds text only: scripts you can read, never a compiled program, an archive or a symlink; secrets are refused, opaque blobs and scripts that fetch and run code are flagged, and a vendor CLI is installed by you and only named. An approved executable is code that runs with your rights; the guard does not contain it, so read it before you approve it.

`provider new` drafts a pack in the library, `~/.qargi/config/packs/providers/NAME/`, unsealed (`provider import` stores one sealed). The guard reads every definition there, sealed or not, to learn which skills and agents directories the runtimes name, and it fails closed: while one definition does not load (not valid JSON, a name that clashes with another or disagrees with its directory), every call of a member that writes, or reads a protected place, is refused, with a message naming the pack, until you fix it (`qargi provider check NAME`) or remove it; a call that needs no such directories (`ls`, `git status`) still runs. Edit a draft that may be broken for a while in a scratch directory outside the library and bring it in with `provider import DIRECTORY` when it is whole.

A capability counts only when the definition claims it and it is verified. A shipped definition carries a `verified_on` date for each; a library definition is verified by `provider check` (the hermetic cases: the agent render, the skills link, the read-only corpus through the guard, an adapter's stub), which records it bound to the definition's hash, so an edit or a reseal makes it stale. What no hermetic case can show (an operating-system sandbox that really holds, a real model id) is recorded with `qargi provider attest NAME CAPABILITY`, which runs and spends nothing itself and is asked each time, with the command, the scratch resources, the smallest model, the ceiling and the expected cost stated first. An extension is enabled for one project with `provider enable PROJECT EXTENSION`; two extensions that add the same thing are refused, and what one provides counts only after its own check.

The rules that do not depend on the runtime: a surface whose read-only barrier is not supported cannot serve the review role, unless you accept that for the project with `qargi provider accept NAME --surface S --no-barrier --asked "..."` (it prints a plan and a token, records `models.accept_no_barrier` and writes the audit log); a runtime with no effort control has the effort dropped and `qargi agent models` says so; a runtime without a per-dispatch model override runs the base with its own model, and a profile with another model is refused; and the output of a read-only run is never applied as patches. For `claude-code` the local barrier is the guard hook (partial: shell writes are caught heuristically and `local verify` is the backstop); the cloud review agents of `claude-platform` have no barrier, so a cloud review role needs your acceptance before it is provisioned or started. A runtime that is not a hook runtime holds a read-only member another way (the runtime's own sandbox flags, or an adapter) or not at all, and what qargi does for any runtime is the same: a git wrapper without credentials, so an ordinary push has nothing to authenticate with; patches checked by `qargi local verify` and `qargi review check` and reviewed before they are applied; and the class recorded by qargi and not by the task text.

The local runtime `codex` (family `openai`, data only) is held and wired as follows. None of its claims is verified yet, so until a live check records them its read-only barrier counts as none and a review role on it needs `provider accept`.

| Part | `codex` |
|---|---|
| Dispatch | `qargi local run` starts `codex exec` in the run's clone with the prompt on standard input; Codex writes the member's last message to a new file of the run (`-o {final_message}`), which qargi checks and publishes as `OUT/report.md` |
| Review output | the report is the member's last message; the lead writes the run's `manifest.json` beside it from its own record, so a read-only run passes `qargi review check` with no `review save` |
| Read-only barrier | the Codex operating-system sandbox, `--sandbox read-only` (a write run gets `workspace-write` with OUT and the clone's `.git` added), claimed `partial`: it holds the member's shell commands, not its reads |
| Commits | a write member commits in its clone and returns patches: `workspace-write` keeps `.git` read-only, so the clone's `.git` is added as a writable directory (`--add-dir {clone}/.git`, seen to let `git add` and `git commit` work with codex-cli 0.167.1). The cost: the member can change its own clone's git configuration and hooks. The clone's only remote is the run's bare copy with its push URL disabled, the sandbox has no network, you take the work from the patches in OUT, and `qargi local verify` compares the real repository's refs. A read-only run never gets it, and a `.git` that is a link refuses the run. A run that leaves a change uncommitted and returns no patches is a refusal: `qargi local run` ends it `refused` (`WORKTREE=uncommitted`) and `qargi review check` fails it unless the manifest says `BLOCKED` |
| Guard hook | not wired: no `qargi __guard` runs, so the publish and skill verbs are held only by the sandbox's write and network denial |
| MCP | each run's own `config.toml` in its `CODEX_HOME` lists, per server, the tools the run's role and class may call (`enabled_tools`); a server runs outside the sandbox, so that list is what holds it |
| Sign-in | your `~/.codex/auth.json`, linked into the run home for the run only; the member sees nothing else of your Codex home, and can read that file through the link |
| Cost | tokens only, added up from the `turn.completed` events; a ChatGPT sign-in reports no money per run |
| Mixed runtimes | not supported: a project has one local runtime, so a project on `codex` runs every member with `qargi local run` |

A runtime's adapter (`lib/providers/NAME/adapter`, or a file of the pack) is optional code behind a small JSON contract (`lib/providers/adapter-schema.json`: resolve, dispatch-local, barrier-check, provision, start-session, status, collect, stop, cost; exit 3 for what the definition says is unsupported), and `bash tests/conformance.sh NAME` runs the conformance cases against it, including a corpus of calls a read-only barrier must allow or deny. The `claude-code` adapter has the local verbs, the `claude-platform` adapter the cloud start-session request builder; its other cloud verbs still run through the existing scripts. A data-only runtime has none; for a command runtime such as `codex` the same command has `qargi local run` start the runtime's stub in place of its command and checks the argv of each class, the prompt, the transcript and its usage, and the member's environment and run home.
