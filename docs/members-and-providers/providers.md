# Providers and runtimes

A **runtime** is one way of running agents on one surface (local or cloud), and it is data: a JSON definition (`lib/providers/schema-2.json`) with the models of each tier and the date and source each was verified on, the effort levels it understands, a capability matrix (model and effort overrides at dispatch, a fixed tool list per agent, a read-only barrier, a session budget ceiling, memory stores, skills, MCP), where its skills, agents, MCP file, settings and memory live and how each is linked into a work tree (a directory link, one link per entry, a copy), how a member is written as the runtime's own file, how a member is dispatched, and how a read-only member is held. A **family** groups the runtimes that share a **model catalog**. Claude ships as the family `claude` with the catalog `claude` and two runtimes, `claude-code` (local) and `claude-platform` (cloud). Three kinds of pack share the provider library, `~/.qargi/config/packs/providers/NAME/`: `provider` (a runtime), `catalog` and `extension` (capabilities a project adds to a runtime). `qargi provider list`, `show NAME` and `check NAME` print them, the matrix and what degrades; a project picks one runtime per surface with `models.provider.local` and `models.provider.cloud`, and there is no default.

Add a runtime with no code: `qargi provider new NAME`, edit the definition ([CONTRIBUTING](../../CONTRIBUTING.md#add-a-runtime-with-no-code) has a worked example), `provider check NAME`, `provider seal NAME`, then `qargi project set P models.provider.local NAME`. A command-line runtime is dispatched by `qargi local run RUN` (`--dry-run` prints the argv, the working directory and the prompt): the argv is an array in the definition, never a shell string, and only the environment variables it names reach the process. A runtime that keeps its settings and sign-in in a directory of its own declares `dispatch.home`: the member gets that directory under the run's home, in the variable the runtime reads, and the files it lists from your home (a sign-in file, never qargi's own files or your ssh, gpg, git, forge or cloud credentials) are linked into it when the run starts and unlinked when it ends. The file is never copied and the dry run names the link only (`HOME_LINKS=`); the member can still read it through the link. `provider import SOURCE` takes someone else's pack from a directory, a JSON file or an https git URL. Every change to the library (`new`, `import`, `seal`, `remove`, `enable`, `disable`, `attest`) is a plan, a token and your approval, and a pack with executables also needs `--approve-exec` naming every one. A pack holds text only: scripts you can read, never a compiled program, an archive or a symlink; secrets are refused, opaque blobs and scripts that fetch and run code are flagged, and a vendor CLI is installed by you and only named. An approved executable is code that runs with your rights; the guard does not contain it, so read it before you approve it.

`provider new` drafts a pack in the library, `~/.qargi/config/packs/providers/NAME/`, unsealed (`provider import` stores one sealed). The guard reads every definition there, sealed or not, to learn which skills and agents directories the runtimes name, and it fails closed: while one definition does not load (not valid JSON, a name that clashes with another or disagrees with its directory), every call of a member that writes, or reads a protected place, is refused, with a message naming the pack, until you fix it (`qargi provider check NAME`) or remove it; a call that needs no such directories (`ls`, `git status`) still runs. Edit a draft that may be broken for a while in a scratch directory outside the library and bring it in with `provider import DIRECTORY` when it is whole.

A capability counts only when the definition claims it and it is verified. A shipped definition carries a `verified_on` date for each; a library definition is verified by `provider check` (the hermetic cases: the agent render, the skills link, the read-only corpus through the guard, an adapter's stub), which records it bound to the definition's hash, so an edit or a reseal makes it stale. What no hermetic case can show (an operating-system sandbox that really holds, a real model id) is recorded with `qargi provider attest NAME CAPABILITY`, which runs and spends nothing itself and is asked each time, with the command, the scratch resources, the smallest model, the ceiling and the expected cost stated first. An extension is enabled for one project with `provider enable PROJECT EXTENSION`; two extensions that add the same thing are refused, and what one provides counts only after its own check.

The rules that do not depend on the runtime: a surface whose read-only barrier is not supported cannot serve the review role, unless you accept that for the project with `qargi provider accept NAME --surface S --no-barrier --asked "..."` (it prints a plan and a token, records `models.accept_no_barrier` and writes the audit log); a runtime with no effort control has the effort dropped and `qargi agent models` says so; a runtime without a per-dispatch model override runs the base with its own model, and a profile with another model is refused; and the output of a read-only run is never applied as patches. For `claude-code` the local barrier is the guard hook (partial: shell writes are caught heuristically and `local verify` is the backstop); the cloud review agents of `claude-platform` have no barrier, so a cloud review role needs your acceptance before it is provisioned or started. A runtime that is not a hook runtime holds a read-only member another way (the runtime's own sandbox flags, or an adapter) or not at all, and what qargi does for any runtime is the same: a git wrapper without credentials, so an ordinary push has nothing to authenticate with; patches checked by `qargi local verify` and `qargi review check` and reviewed before they are applied; and the class recorded by qargi and not by the task text.

A runtime's adapter (`lib/providers/NAME/adapter`, or a file of the pack) is optional code behind a small JSON contract (`lib/providers/adapter-schema.json`: resolve, dispatch-local, barrier-check, provision, start-session, status, collect, stop, cost; exit 3 for what the definition says is unsupported), and `bash tests/conformance.sh NAME` runs the conformance cases against it, including a corpus of calls a read-only barrier must allow or deny. The `claude-code` adapter has the local verbs, the `claude-platform` adapter the cloud start-session request builder; its other cloud verbs still run through the existing scripts. A data-only runtime has none.
