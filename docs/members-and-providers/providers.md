# Providers and runtimes

A **runtime** is one way of running agents on one surface (local or cloud), and it is data: a JSON definition (`lib/providers/schema-2.json`) with the models of each tier and the date and source each was verified on, the effort levels it understands, a capability matrix (model and effort overrides at dispatch, a fixed tool list per agent, a read-only barrier, a session budget ceiling, memory stores, skills, MCP), where its skills, agents, MCP file, settings and memory live and how each is linked into a work tree (a directory link, one link per entry, a copy), how a member is written as the runtime's own file, how a member is dispatched, and how a read-only member is held. A **family** groups the runtimes that share a **model catalog**. Claude ships as the family `claude` with the catalog `claude` and two runtimes, `claude-code` (local) and `claude-platform` (cloud). Three kinds of pack share the provider library, `~/.qargi/config/packs/providers/NAME/`: `provider` (a runtime), `catalog` and `extension` (capabilities a project adds to a runtime). `qargi provider list`, `show NAME` and `check NAME` print them, the matrix and what degrades; a project picks its own runtime for each surface with `models.provider.local` and `models.provider.cloud`, and there is no default; the owner may enable more local runtimes beside the project's own ([More than one local runtime in a project](#more-than-one-local-runtime-in-a-project)).

Add a runtime with no code: `qargi provider new NAME`, edit the definition ([CONTRIBUTING](../../CONTRIBUTING.md#add-a-runtime-with-no-code) has a worked example), `provider check NAME`, `provider seal NAME`, then `qargi project set P models.provider.local NAME`. A command-line runtime is dispatched by `qargi local run RUN` (`--dry-run` prints the argv, the working directory and the prompt): the argv is an array in the definition, never a shell string, and only the environment variables it names reach the process. Its command word is resolved on your `PATH`, entry by entry, to the first regular executable file whose real path has that name (or the name with an extension, such as a launcher `NAME.js`, or with a suffix after a dash, such as a release binary `NAME-x86_64-unknown-linux-musl`), and that path runs: the dry run prints it (`COMMAND=`) and `RUN/dispatch.json` records it (`command`). A wrapper or shim that is a link to a program of another name, as a version manager installs, is passed over with a note, because under the run's home it would look for the tool there; when nothing else is left the run is refused (exit 3), naming each entry and why. A shim that is a script of the command's own name cannot be told apart and runs as found. The member's own `PATH` is yours, unchanged, wrappers for other tools included, and those run under the run's home too ([Codex as lead and as member](codex.md#platform-and-sandbox) says what follows). A runtime that keeps its settings and sign-in in a directory of its own declares `dispatch.home`: the member gets that directory under the run's home, in the variable the runtime reads, and the files it lists from your home (a sign-in file kept for members, never qargi's own files, the sign-in of your own sessions of the runtime, or your ssh, gpg, git, forge or cloud credentials) are linked into it when the run starts and unlinked when it ends. A member signs in on its own: a link source that does not exist (a link to a missing file too), is not a regular file or resolves inside the directory where the runtime keeps your own sessions (the directory of the definition's `resources.instructions.user_file`, `resources.skills.exclusion.file` or `resources.skills.user_dir`) refuses the run (exit 2: `qargi local prepare` before it makes anything, `qargi local run` before it starts anything), naming the path as the definition declares it and the login that makes it (`VAR=DIR COMMAND login`, with the variable of `dispatch.home.env`). The runs that share a plain link's source run one at a time: an exclusive lock on `.qargi-run.lock`, in the directory of the source's real file, is held from before the links are made until they are removed, and a second run prints that it waits and does (a signal ends the wait); a directory that cannot be written refuses the run, which never starts without the lock. A runtime that refreshes the sign-in it is given in place can declare the link private (`"private": {"set": {"PATH": "text"}, "expiry": {"path": "PATH", "encoding": "jwt-exp", "margin_seconds": 900}}`; `provider show` and the review name such a link as a copy): the source is a JSON file, and each run gets a copy of its own, a regular file of the run home (mode 600, made exclusively, removed when the run ends), with each text of `set` put at its dotted path, a placeholder in place of the refresh token; the runs that share such a source take no lock and overlap, and a definition with a private and a plain link takes the lock for the plain one. The value at `expiry.path` is read by its encoding (`jwt-exp`: the `exp` claim of a JWT, no signature checked, never printed or recorded) and a run whose bound (`timeout_s`, or `--timeout`) plus `margin_seconds` (default 900) is more than that value has left is refused before it starts (`runtime-signin-expiring`, exit 1; nothing made or recorded; and again once the locks are held), naming the declared path, the seconds left, the bound, the margin and the login; a source that is not a JSON object or has no such value is refused (exit 2). Nothing is written back to the source. A plain link's source is never copied: a run prints no path of a link's source, and the dry run names each link with the file it points at (`HOME_LINKS=NAME<-PATH`), each private copy with the file it is made from (`HOME_COPIES=NAME<-PATH`), and `RUN/dispatch.json` records `home.private`; the member can still read a plain link's file through it, and a private copy still hands the member a live access token in its own home. A runtime that holds the MCP tools of a server in the server's entry (`resources.mcp.tool_lists`) can declare `dispatch.run_config`: each run then gets its own configuration file, in the run home (`in: home`, for a runtime that reads its configuration from there) or in `RUN/config` (`in: run`, passed with `{run_config}` in the argv), listing the tools a member may call for the run's role and class (never an `always_ask` tool, under the read-only class only a declared read; the role is the one the lead's registry records). A definition can also give the file a `baseline`, settings of the runtime's own configuration written into every run's file whatever tools reach the role, so a run with no MCP server and a run with one get the same settings; without a baseline a run whose role no tool pack reaches gets no file. The dry run prints the file's path, the tool names and the baseline (`RUN_CONFIG=`, `RUN_CONFIG_TOOLS=`, `RUN_CONFIG_BASELINE=`), never the servers' addresses. For `codex` it is `CODEX_HOME/config.toml` in the run home, the user-level configuration of the member's Codex; it is not all a member's Codex reads ([Codex as lead and as member](codex.md) has what loads and what does not). A runtime whose sandbox hides part of the filesystem from the member declares `dispatch.hidden_paths`: the path `prefixes` it hides, per class the run paths it `shown` anyway (the places it binds in, such as a write class's writable directories) and a `note` saying why. A read-only member works with its clone, its contract and its git wrapper, a write member also with OUT and TMP (the task block reaches it in the prompt); when one of those that its class does not show lies under a prefix, by its path or its real path, `qargi local prepare` refuses the run before it makes anything and `qargi local run` before it starts anything (exit 2), naming the path, the prefix and the fix (`--scratch` on another filesystem, or `QARGI_RUN_TMP`). `codex` declares `/dev`, so a run whose scratch directory is under `/dev/shm` is refused for it; use a directory on disk. A runtime that writes the member's last message to a file it is given names `{final_message}` in its argv: a file in a directory of the run made new for each run, never a file of OUT. When the run ends qargi takes it only as a regular file with one name, of text, at most 1 MiB (a link, a pipe, a directory or a second name of another file is not followed, read or published), publishes it as `OUT/report.md` by renaming a new file over that name, and prints `REPORT=` (and records `report` in `RUN/dispatch.json`). On `--again` the report of the earlier run is set aside as `OUT/report.md.previous` before the member starts: a run that publishes a report replaces it (`PREVIOUS_REPORT=replaced`), and a run that publishes none, a failed one for instance, leaves it there (`PREVIOUS_REPORT=kept`), where no check takes it for this run's report. A `report.md` that is not a plain file of its own refuses the run before anything starts. A read-only member may write nothing, so for a read-only run with such a file the lead also writes `OUT/manifest.json`: the minimal report-only manifest that `qargi review save` writes (status, base, no commits, the report in `artifacts`) with what the lead recorded of the run under `run` (its id, role, runtime, class, the model and effort qargi passed, start, seconds, exit and outcome), taken from the lead's registry and `RUN/refs.before`, never from the member. It is written only when the outcome is ok, the report was published and OUT holds no patch (`MANIFEST=`, or `MANIFEST=none: WHY`), and it claims no test and no verdict: `qargi review check` still reads the Findings and the verdict line of the report, and refuses a report without them as before. The run then goes through `qargi local verify`, `qargi review check` and `qargi local clean` like any review run, with no `review save`. The model and effort it names are what qargi passed, not what the runtime confirmed. `provider import SOURCE` takes someone else's pack from a directory, a JSON file or an https git URL. Every change to the library (`new`, `import`, `seal`, `remove`, `enable`, `disable`, `attest`) is a plan, a token and your approval, and a pack with executables also needs `--approve-exec` naming every one. A pack holds text only: scripts you can read, never a compiled program, an archive or a symlink; secrets are refused, opaque blobs and scripts that fetch and run code are flagged, and a vendor CLI is installed by you and only named. An approved executable is code that runs with your rights; the guard does not contain it, so read it before you approve it.

Command runtimes may declare optional `dispatch.home.skills_dir`, a plain relative directory inside `RUN/home/DIR`. Its first component must avoid credential destinations, their `.from-run` residues and an in-home `run_config.file`; symlink traversal refuses. Structural support is separate from observed skills capability and requires no provider-specific code. `{skills_dir}` in resource templates keeps its existing project-resource meaning. Opted-in in-session delivery refuses. Atomic managed delivery requires the run and private lifecycle state on one filesystem. See [managed member snapshots](../../skills/qargi-packs/member-skills.md) for the owner gate, bounds and lifecycle contract.

`provider new` drafts a pack in the library, `~/.qargi/config/packs/providers/NAME/`, unsealed (`provider import` stores one sealed). The guard reads every definition there, sealed or not, to learn which skills and agents directories the runtimes name, and it fails closed: while one definition does not load (not valid JSON, a name that clashes with another or disagrees with its directory), every call of a member that writes, or reads a protected place, is refused, with a message naming the pack, until you fix it (`qargi provider check NAME`) or remove it; a call that needs no such directories (`ls`, `git status`) still runs. Edit a draft that may be broken for a while in a scratch directory outside the library and bring it in with `provider import DIRECTORY` when it is whole.

A command runtime that writes a configuration file for each run (`dispatch.run_config`) may also declare **options** there, `dispatch.run_config.options.NAME`: an opt-in change to that file, as data. An option names the settings it flips (`set`: keys the baseline already holds as false, set to true; nothing else, never an MCP server), the classes it is for (`classes`: write only), whether the tool it opens runs outside the sandbox (`outside_sandbox`) and may spend (`spends`: `no`, `yes` or `unknown`), where it may write (`writes`), the words the owner's approval must contain (`phrase`, in lower case), and `verified_on`, `source` and `note`. `provider check` refuses a `set` that adds a key the baseline lacks, touches the MCP servers, or sets anything but a baseline `false` to `true` (a string, a number, a list, a table, `true` to `false`), a missing `phrase`, and a class other than write. An option does nothing by itself: the owner enables it for a project's runtime with `qargi provider enable PROJECT --runtime NAME --option OPT` (a plan, a token and words that carry the phrase, which the approval binds to the declaration as it was shown: a definition that changes the option afterwards is refused when a run is prepared until the owner approves it again), a profile of the project selects it (`profiles.NAME.options`), and only a run of that profile gets the baseline with the option's settings over it. A project and a profile that select none get the run file, the prepare and run output and the plans they always had. The shipped `codex` definition declares `image_generation` this way ([Codex](codex.md#image-generation-an-opt-in-off-by-default)).

A capability counts only when the definition claims it and it is verified. A shipped definition carries a `verified_on` date for each; a library definition is verified by `provider check` (the hermetic cases: the agent render, the skills link, the read-only corpus through the guard, an adapter's stub), which records it bound to the definition's hash, so an edit or a reseal makes it stale. What no hermetic case can show (an operating-system sandbox that really holds, a real model id) is recorded with `qargi provider attest NAME CAPABILITY`, which runs and spends nothing itself and is asked each time, with the command, the scratch resources, the smallest model, the ceiling and the expected cost stated first. An extension is enabled for one project with `provider enable PROJECT EXTENSION`; two extensions that add the same thing are refused, and what one provides counts only after its own check.

The rules that do not depend on the runtime: a surface whose read-only barrier is not supported cannot serve the review role, unless you accept that for the project with `qargi provider accept NAME --surface S --no-barrier --asked "..."` (it prints a plan and a token, records `models.accept_no_barrier` and writes the audit log); a runtime with no effort control has the native effort argument dropped, while command-mode `qargi agent models` retains the requested level; an in-session runtime without a per-dispatch model override runs the base with its own model, and a profile with another model is refused; and the output of a read-only run is never applied as patches. For `claude-code` the local barrier is the guard hook (partial: shell writes are caught heuristically and `local verify` is the backstop); the cloud review agents of `claude-platform` have no barrier, so a cloud review role needs your acceptance before it is provisioned or started. A runtime that is not a hook runtime holds a read-only member another way (the runtime's own sandbox flags, or an adapter) or not at all, and what qargi does for any runtime is the same: a git wrapper without credentials, so an ordinary push has nothing to authenticate with; patches checked by `qargi local verify` and `qargi review check` and reviewed before they are applied; and the class recorded by qargi and not by the task text.

A definition's `notes` say how the runtime does what a skill asks of it, one topic to one line of text, and `qargi provider notes [TOPIC]` prints them for the project's runtime, so the skills point at a topic and name no runtime's tools. Some notes are about the lead's own session on that runtime and some about the members the runtime runs, and the definition says which: `lead_notes` lists the topics of its `notes` that are about the lead's session, and every topic it does not list is about its members. A definition that lists none says that all its notes are about its members. `qargi provider check` fails a listed topic the notes do not have, a topic listed twice and a value that is not a list of names; an extension cannot add the list. The shipped runtimes:

| Runtime | About the lead's own session (`lead_notes`) | About its members |
|---|---|---|
| `claude-code` | `commands`, `exploration`, `identity`, `session-model`, `skills-dir` | `spawn`, `member-out` |
| `codex` | `commands`, `exploration`, `identity`, `session-model`, `skills-dir` | `spawn`, `message` |
| `claude-platform` (cloud) | none | `clone-dir`, `output-dir` |

`spawn` is about the members: how a member is started depends on the runtime the member runs on (a tool of the session for an in-session runtime, `qargi local run` for a command runtime), whatever runtime the lead's session is. A command any lead can run; a tool of the session only a lead whose session is on that runtime has, which is why a lead on another runtime is refused the `spawn` note of an in-session runtime (below). `message` of `codex` is not listed either: it says how a message reaches a session on that runtime, which is a fact about those sessions for whoever writes to one, not guidance for a lead whose own session is on `codex`.

A lead whose own session runs on another runtime than the project's members names it: `qargi provider notes [TOPIC] --lead-runtime NAME`, or `QARGI_LEAD_RUNTIME=NAME` in the session's environment (the option wins; an empty variable is none). The topics the lead runtime lists in `lead_notes` are then answered by the lead runtime, and every other topic by the project's runtime as before; the list of topics is both. So a lead on `claude-code` of a project whose members run on `codex` reads its own `identity` and `session-model` from `claude-code` and `spawn` and `message` from `codex`, and a lead on `codex` of a project on `claude-code` reads its own `identity` and `session-model` from `codex`; that lead cannot start the project's members (below). With neither the option nor the variable, every note is the project's runtime's, as it was before the list existed.

- **The name**: a runtime of the local surface (a lead's session is a local one, whatever `--surface` asks about the members), with a definition that can be used as it stands (shipped, or a library pack that is sealed), given by its own name and not by a family's. Any other name is `unsupported`, exit 3, whatever topic is asked; the message lists the local runtimes there are and says whether the option or the variable named it (a name from the environment is not on the command line you see refused).
- **A note the lead runtime lacks**: a topic the project's runtime lists as about a lead's session, and the lead runtime does not, is `unsupported`, exit 3. The project's runtime's text is for a lead on that runtime and is never printed in its place (the shipped runtimes list the same five topics, so this arises with a runtime of your own that lists another). A topic neither has is exit 1, as an unknown topic always was.
- **Members only a lead on their runtime can start**: a runtime whose `dispatch.mode` is `in-session` starts a member with a tool of the lead's own session, so its `spawn` and `member-out` notes are instructions for a lead on that runtime. When the lead runtime is another one, both are `unsupported`, exit 3: the message says that members of this project cannot be started from this lead and names the two runtimes, the text is never printed (it would send the lead to a tool it does not have), and the list of topics leaves the two out. The runtime's other notes about its members are answered, and so are the lead's own. A lead on `codex` of a project on `claude-code` is in that position: to start members, the lead must be a session on `claude-code`, or the project's local runtime one that `qargi local run` starts. A lead on the project's own runtime, and one that names no lead runtime, read both notes as before.
- **Independence**: a topic the lead runtime lists needs the project, not the project's runtime, so a lead reads its own guidance also when the project has no local runtime or its definition cannot be read; a note about members, and the list, are refused then as without a lead runtime (exit 2).
- **What it does not do**: the name selects which definition is read and nothing else. The project's answers, the members' settings and the stored runtimes are not written, the lead identity (`QARGI_LEAD`, `--as`) is not derived from it, and no approval, permission or guard decision depends on it. Members are still started as the project's runtime says (its `spawn` note): naming a lead runtime gives a lead no new way to start a member, and `qargi local run` still refuses a runtime that works inside the session.
- **qargi's own questions**: `qargi team brief` and `qargi collect` ask the project's cloud runtime where a hosted session keeps its outputs and its clones (`output-dir`, `clone-dir`). They ask with `QARGI_LEAD_RUNTIME` cleared, so the answer is the cloud runtime's whatever the variable holds: a name in it that is no usable runtime does not refuse them, and a lead runtime that lists such a topic as its own does not answer in the cloud runtime's place.

The local runtime `codex` (family `openai`, data only) is held and wired as follows; [Codex as lead and as member](codex.md) has the details, a Codex lead's setup and a complete run. Three of its claims are verified by live checks with codex-cli 0.167.1 on 2026-11-11 and dated in its definition: headless dispatch (a write-class run end to end), the read-only barrier (partial: the sandbox refused a shell write offline and in a live read-only member) and the token report, so a review role runs on it with the barrier's note and needs no `provider accept`. The model and effort overrides (accepted in a run, but no event names them), skills and MCP stay unverified and count as not supported.

- **Dispatch**: `qargi local run` starts `codex exec` in the run's clone with the prompt on standard input; Codex writes the member's last message to a new file of the run (`-o {final_message}`), which qargi checks and publishes as `OUT/report.md`
- **Review output**: the report is the member's last message; the lead writes the run's `manifest.json` beside it from its own record, so a read-only run passes `qargi review check` with no `review save`
- **Read-only barrier**: the Codex sandbox, `--sandbox read-only` (a write run gets `workspace-write` with OUT and the clone's `.git` added), verified `partial` (codex-cli 0.167.1, 2026-11-11): it holds the member's shell commands, not its reads, and not a hosted tool or an MCP server. qargi runs on Linux only, where codex-cli's sandbox is bubblewrap (`codex sandbox`: a read-only root, seccomp, no network); Codex's macOS sandbox plays no part
- **Configuration**: the run's `config.toml` in its `CODEX_HOME` always carries the definition's baseline: `approval_policy` `never`, no shell network, no `/tmp` (the run's `TMPDIR` stays writable), hosted web search, apps, plugins, hooks and the bundled skills off; `--ignore-rules` drops every rules file and `--strict-config` refuses an unknown key. Your Codex configuration is not loaded (`CODEX_HOME` and `HOME` are the run home), nor the clone's `.codex/` (a run clone is never trusted), while the clone's `AGENTS.md` is; a system-wide or managed Codex configuration is not excluded. Each key is read by codex-cli 0.167.1 (seen offline); that each holds in a real run is not yet verified
- **Skills**: managed delivery defaults off. An owner-gated opt-in snapshots the actual role's reviewed canonical skill selection into the private runtime home. Committed checkout skills remain independently discoverable. The Codex guide records two headless marker observations and their limits; interactive loading and the complete client inventory remain unqualified.
- **Commits**: a write member commits in its clone and returns patches: `workspace-write` keeps `.git` read-only, so the clone's `.git` is added as a writable directory (`--add-dir {clone}/.git`, seen to let `git add` and `git commit` work with codex-cli 0.167.1). The cost: the member can change its own clone's git configuration and hooks, and a hook, `core.fsmonitor`, an alias or a filter driver set there runs as you when you run git in that clone. `qargi local run` reads the clone's `.git/config`, `hooks/` and `info/` before the member starts and compares them when it ends, for every run whose argv grants the clone's `.git` and every run whose class has no sandbox arguments: a change other than what `git branch` sets (`branch.NAME.remote` and the like) is named in a `GITDIR=changed:` line and in `git_dir` of `RUN/dispatch.json`, by key and entry, never a value; nothing is restored. Never run git in a write member's clone: take the work from the patches in OUT, copy files out, or make a clean copy first with `git clone --no-local`, as git(1) advises under SECURITY. The clone's only remote is the run's bare copy with its push URL disabled, the sandbox has no network, you take the work from the patches in OUT, and `qargi local verify` compares the real repository's refs. A read-only run never gets it, and a `.git` that is a link refuses the run. A run that leaves a change to a tracked file uncommitted and returns no patches is a refusal: `qargi local run` ends it `refused` (`WORKTREE=uncommitted`) and `qargi review check` fails it unless the manifest says `BLOCKED`. New files never added are reported (`WORKTREE=untracked`, a warning in review check), not refused, and `qargi local clean` warns when it removes them with the clone
- **Guard hook**: not wired: no `qargi __guard` runs, so the publish and skill verbs are held only by the sandbox's write and network denial, the credential-free git wrapper and the checks of what comes back
- **MCP**: each run's own `config.toml` in its `CODEX_HOME` lists, per server, the tools the run's role and class may call (`enabled_tools`, the server's own names; the model sees them as `mcp__SERVER__TOOL`); a server runs outside the sandbox and the shell's network denial does not hold it, so that list is what holds it. An authenticated server gets only its `url`: no vault value, bearer token or token variable is written, so it fails to connect in a member run
- **Sign-in**: the members' sign-in, `~/.codex-members/auth.json`, linked into the run home for the run only, as a private copy (a regular file, mode 600, with a placeholder in place of the refresh token), and never your own `~/.codex/auth.json`: Codex runs outside its own sandbox and refreshes the token, so through a link to your own file it could change that file, or replace the link, and where the token rotates the one left in your file can be revoked and sign you out of your own Codex; two runs at once, each refreshing one file, would race on its token, which is why the copy has no refresh token. Make the members' sign-in once, in your terminal, with a directory of its own, which must exist before the login: `mkdir -p ~/.codex-members && chmod 700 ~/.codex-members && CODEX_HOME=~/.codex-members codex login`. A run is refused (exit 2, `qargi local prepare` too) when that file is missing, is not a regular file or resolves inside `~/.codex`, naming the path and that login; the runs that share it overlap, for each gets a private copy that cannot refresh (below), and a run that would outlive the copy's access token is refused before it starts (`runtime-signin-expiring`; the lead signs in again with the login). The file is checked again just before it is copied and the copy is read once; the run has a file of its own, and only the same user can write the members' directory. If your own `CODEX_HOME` is `~/.codex-members`, your Codex shares the sign-in and its token refreshes change the file the runs copy. The result of a check of a definition (`provider check`, the seal) depends on your `CODEX_HOME` and on the file system (a link in the path of the source). The member's Codex loads nothing else of your Codex home (its settings, sessions and hook trust). This is configuration separation, not secrecy: the sandbox holds writes, not reads, so the member can still read the members' file through the link and the rest of your `~/.codex` (sessions, history) by path. What the member does to its copy goes with the run and never reaches the members' file (a note names a copy that changed). For a plain link (a sealed library copy of the definition may declare one), a sign-in Codex refreshes during the run is not lost, and qargi never writes the members' file: written through the link, it lands in that file directly (qargi cannot prevent that; a note says the file changed); written by replacing the link with a new file, it is kept as `auth.json.from-run` (mode 600) in the run home, named in a `HOME_RESIDUE=` line and in `home.residue` of `RUN/dispatch.json`, with a note that says whether the members' file is unchanged since the run started (compared by a hash kept in memory, never printed), and you reconcile it yourself ([codex.md](codex.md#what-a-member-can-reach)). Which way codex-cli writes is not verified yet. Only a file store is linked: Codex can keep its sign-in in the system keyring instead (a `cli_auth_credentials_store` setting, seen in codex-cli and not verified), and then the members' directory has no `auth.json` to link and the run is refused as above. A `CODEX_HOME` of yours that is another directory than `~/.codex-members` is a note: the run links `~/.codex-members/auth.json` only
- **Ending a run**: the link goes when the run ends, also when it fails, times out, cannot start, or the runner gets SIGINT, SIGTERM or SIGHUP. On normal exit as well as interruption, the original process group gets TERM and is watched for up to 5 seconds, then KILL for what is left. Cleanup precedes removal of the link and inspection of output. Survivors are counted, and a successful run with survivors fails. A process that moved to another process group is not contained. SIGKILL of the runner leaves `RUN/dispatch.json` saying `running`; `qargi local list` and `qargi local verify` name the link, the next start refuses while the member still runs and otherwise needs `--again`, and `qargi local clean` removes the run with it
- **Cost**: tokens only (verified in live runs, codex-cli 0.167.1, 2026-11-11), added up from the `turn.completed` events; a count no event reports is named as not reported, never recorded as 0; a ChatGPT sign-in reports no money per run
- **Resume**: none: every run is a fresh `codex exec --ephemeral` session
- **Reads**: not confined (`dispatch.reads` of the definition: `{"confined": false, "exposes": ["~/.codex"], "note": "sessions, history, sign-in"}`): a member on `codex`, read-only or not, can read whatever the lead's account can read outside `/dev`, the real `~/.codex` among it. 0.3.6 allows that with a warning and the owner's approval words ([below](#more-than-one-local-runtime-in-a-project)), and does not confine it yet
- **Mixed runtimes**: a project runs members on its own local runtime and on the runtimes the owner enabled beside it ([below](#more-than-one-local-runtime-in-a-project)); a project on `codex` can send chosen tasks to another command runtime, and a project on `claude-code` can send them to `codex`

Unexpected runner errors preserve the start time, runner and member identity, planned home link names, refreshed file residue and cleanup notes in `dispatch.json`; credential contents and exception text are never copied into that error record. `group_left` is null when survivors could not be counted, and absent when no member started. `local list` and `local verify` still show retained links and `.from-run` files. A retry checks the original group even when the outcome is `refused`: known survivors or an unknown group state block `--again` until quiescence can be established. This check sends no signal to a recorded PID, whose identity may have changed. Processes that leave the original group and generalized recycled-PID cleanup remain outside this guarantee. If partial home setup and its cleanup both fail, the record retains planned link names and cleanup notes even when setup never returned its list of created links, including an expected refusal. An unreadable group probe does not prevent TERM-to-KILL escalation; the final survivor state remains unknown. Hosts that prevent inspection of process groups may refuse runs and retries. Even a previously completed run can refuse a retry if its recorded group ID has been reused; preserve wanted work before deliberate discard.

The lead verbs' run permissions and the guard's MCP policy use the lead registry's exact decoded JSON class, `write` or `read-only`; Unicode escapes that decode exactly to either string work, while trailing newlines, NULs, whitespace, other labels and nonstrings refuse. A member's class file supplies no fallback for those decisions. Pre-existing guard tightening of shell and write calls still consults that file; its authority migration and generalized heuristic changes are outside this change. Ordinary clean, verify, apply, run and report preserve a run with an unknown class. Explicit `qargi local clean RUN --discard` can recover a known registered legacy run without a class, whether its directory exists or is gone; it intentionally drops the run's evidence and saved output, subject to the other discard protections, including a live apply lock and refusal to remove a linked run directory. An unregistered run cannot be discarded by qargi. Deliberate discard closes the known record so compact-check can recover. Inside a member, `qargi review check OUT` first requires `QARGI_MEMBER_RUN` to resolve to the inspected run (the parent of OUT, or RUN when given directly), then checks the output's structure without requiring or borrowing lead registry state and without running lead inspection or scrub, writing verification, or making trusted scrub marks or cache. A mismatched marker refuses. HOME normally lies under the run but is not checked as the marker contract; the marker grants no lead authority. The lead must still check the result with strict registry class validation, followed by lease renewal and the declared scrub.

Inspection supports plain prepared clones with default files ref storage, repository format 0 or 1, SHA-1 or SHA-256 objects, and no Git extensions beyond `objectFormat`, only within the bounds below. Trusted run ancestors are canonicalized, so an owner-controlled ancestor link is allowed; clone and `.git` must be plain directories. Git reads a private metadata copy under the lead's trusted state directory, outside clone and OUT, with a newly written minimal config. The inspection Git is an absolute executable resolved once from the lead's clean controlled PATH; a member's later PATH cannot choose it. System and global configuration and inherited Git environment are scrubbed; `GIT_NO_REPLACE_OBJECTS=1` keeps replacement refs from changing original commit counts or status semantics. The source config is parsed from a private file without following includes; only the object format and closed values of `core.filemode`, `ignorecase`, `symlinks`, `autocrlf` and `eol` are retained. Valueless booleans stay true and explicit empty booleans stay false, as Git defines them. SHA-1 uses a format-0 minimal config without an unnecessary extension; SHA-256 explicitly uses format 1 and `objectFormat`. The regression tests cover Linux Git, not old Git or native macOS/Windows. Member hooks, fsmonitor, filters, transport, pager, editor and other configured helpers never run during inspection, including when an unknown filter is inserted after preflight. The copied index keeps its source timestamp so same-length changes within a filesystem clock tick remain detectable.

Metadata reads use directory descriptors without following links: copied files must be regular and copied directories plain. Inspection refuses gitfiles, commondir, worktree configuration, config includes, unsupported extensions or ref storage, reftable, `info/grafts`, shallow metadata, `sharedindex.*`, and object alternates (`objects/info/alternates` and `http-alternates`), including linked or special entries at those paths. Hooks and info attributes are not copied. The entire object store and refs, HEAD, config, index and packed refs are copied, bounded by a total of 512 MiB of regular-file bytes, 100,000 traversal/read steps (directory enumeration, copied nodes and each block read of up to 1 MiB), 64 directory levels below each selected top-level entry and a 60-second traversal budget. Config is limited to 1 MiB, and each Git subprocess to 60 seconds. These fixed 0.2.13 limits apply to ordinary prepared clones too; they cannot be raised by config. Sanitized reasons distinguish bounds, unsupported metadata, unreadable storage and Git failures in run, verify, review check and clean; no arbitrary config contents, exception secrets or Git stderr are included. Failure stays unknown. Ordinary clean preserves all artifacts before any removal if either commit or worktree inspection is unknown. Explicit discard remains deliberate recovery: first copy patches, reports, wanted files and `.from-run` residue out, since it removes run, TMP and saved evidence. Making a clean copy does not by itself bring an oversized object store within bounds. A copy can combine concurrent states and does not contain escaped sessions; SIGKILL can leave a private inspection directory, and no stale-directory sweeper is included. Unexpected exceptions after member start also stop the original process group before removing sign-in links; the original exception is preserved if stopping or unlinking also fails. The dispatch record keeps the survivor count, or null when it cannot be determined, and never claims an unknown group stopped.

`feature finish` validates stored project answers and strictly parses one registry snapshot, then enumerates those same records. Missing or malformed answers, unknown repo/url identity, dangling or unreadable registry files, damaged registry records and reader errors refuse. Exit 0 requires an empty response, while exit 1 requires valid open-run rows; an empty exit 1 or traceback is an error. Repository identity is required for any run path that exists or cannot be inspected. A structurally valid record with missing identity is ignored as inactive only when its normalized run path is confirmed absent; an existing path, dangling link or inaccessible path refuses. This rule applies to all records regardless of age, never rewrites or deletes them, and grants no authority. General diagnostic readers may remain tolerant. The gate no longer validates one read before a separate tolerant reread, but it does not serialize new preparation through the eventual merge; atomic membership is not claimed.

When the registered run directory still exists, explicit discard without a valid class compares the authoritative repository refs and reports their actual unchanged or changed verdict before continuing deliberately. This internal refs-only observation grants no class permission, writes no verification mark and saves no accepted output. Ordinary clean independently preserves a read-only run that unexpectedly holds patches or a bundle, including when its clone has zero extra commits; a refs verdict does not accept that product. Explicit discard can deliberately remove it and still reports the actual refs verdict. If the run directory is already gone, discard drops its registry record and any saved copy without a new refs comparison. Ordinary verify still refuses an unknown class. Preserve or copy wanted legacy work before destructive discard; changing the member's class file does not make it authoritative.

A runtime's adapter (`lib/providers/NAME/adapter`, or a file of the pack) is optional code behind a small JSON contract (`lib/providers/adapter-schema.json`: resolve, dispatch-local, barrier-check, provision, start-session, status, collect, stop, cost; exit 3 for what the definition says is unsupported), and `bash tests/conformance.sh NAME` runs the conformance cases against it, including a corpus of calls a read-only barrier must allow or deny. The `claude-code` adapter has the local verbs, the `claude-platform` adapter the cloud start-session request builder; its other cloud verbs still run through the existing scripts. A data-only runtime has none; for a command runtime such as `codex` the same command has `qargi local run` start the runtime's stub in place of its command and checks the argv of each class, the prompt, the transcript and its usage, and the member's environment and run home.

## More than one local runtime in a project

A project has one **own** local runtime, `models.provider.local`, and the owner may enable more beside it: `models.extra_runtimes.local`, a list of runtime names. The **enabled set** of a project is its own runtime plus that list, each once, the own runtime never in the list. `qargi provider runtimes PROJECT` prints it (`primary NAME`, then `extra NAME` for each), read-only and open to a member. A project without the list, or with an empty one, has no extra runtime and sees no change anywhere: no new word, key, line or digest, and no run prepared before an upgrade goes stale. The step-by-step use is in [Sending tasks to a second runtime](several-runtimes.md).

- **What an extra runtime is.** A command runtime of the local surface, started by `qargi local run`: a shipped definition, or a library pack that is sealed and unchanged since. An in-session runtime (one a session of the lead starts) cannot be an extra one. The own runtime is not an extra one, a name is listed once, and a runtime that fails any of this is refused as `runtime-unusable`, naming which condition fails.
- **Enabling is the owner's approval.** `qargi provider enable PROJECT --runtime NAME` prints a plan and a token and changes nothing; `--plan TOKEN --approved WORDS` stores the list through the gated writer and writes one audit line. `provider disable PROJECT --runtime NAME` takes one out, with a plan and a token too, and is refused (no token) while a profile still names the runtime. `qargi project set` refuses `models.extra_runtimes` and names the verb, and so does the import of an archive: an archive can drop an entry of the stored list but never add or change one. The guard refuses `provider enable|disable` to a member.
- **What the plan prints.** The runtime, its origin and the executable it would resolve; each link source of its run home as `FROM -> TO` with the real path, `present` or `missing`, and that it is not inside `~/.codex` (a source that `local prepare` would refuse refuses the plan too, with no token), for a shipped runtime and a library pack alike; that runs sharing a plain link's source run one at a time and a private copy's runs overlap; the whole read-only barrier note; that a read-only role on it runs under the partial barrier, with no `provider accept` asked and none counting; that a read-only member on it is a reading review (below); that its model and effort are requested, not confirmed, while the definition's override claims are unverified; the reads warning; the tool packs each role of the project would get on it, and that the MCP servers of tool packs run outside the sandbox (the list is read at plan time, and a pack linked later is not approved again); the hidden paths; and what the runtime lacks (a guard hook, managed member skills, pack renders).
- **Reads are not confined.** A runtime's definition says what its sandbox does not hold in `dispatch.reads`, `{"confined": bool, "exposes": [paths], "note": text}`; a command runtime whose definition has none counts as not confining reads, with no path named, and a malformed one fails `qargi provider check`. For `codex` the claim is `confined: false`, `exposes: ["~/.codex"]`, `note: "sessions, history, sign-in"`. For such a runtime the plan says, in these words with the definition's paths, that members on it can read the real `~/.codex` (sessions, history, sign-in) and whatever else the account can read: reads are not confined, and it prints the phrase the approval must carry. `provider enable` stores nothing unless the owner's `--approved` words contain `reads are not confined` (letter case and runs of blanks ignored, matched as whole words); otherwise it refuses with `runtime-reads-unacknowledged` and the token stays good. The words are the owner's: the lead passes them on and never writes the phrase itself, and the audit log keeps them. `disable` asks for no phrase. `qargi provider reads-warning NAME` prints the warning line alone. The places that make such a runtime the project's own print the same warning and ask for no phrase: the plan of `project new` (with `--url`, which stores the answers) and of `project attach` (`--provider`, `--provider-local`) and `project set PROJECT models.provider.local NAME`. `project validate` and every other verb stay quiet about it. 0.3.6 does not confine reads; it says so and asks the owner to say so back.
- **Which runtime a task uses.** In this order: the task's `--runtime` (`qargi agent for ROLE --runtime NAME`, `qargi local prepare --runtime NAME`), then the `runtime` of the task's profile (`profiles.NAME.runtime`, a plain `project set` that selects among runtimes already approved and that the guard refuses to a member), then the project's own. A runtime that is not enabled is `runtime-not-enabled`, for a project without extras too. The profile is resolved in that runtime: its tier through the runtime's catalog, its effort through the runtime's levels. `--runtime` against a profile that names another runtime resolves the tier again, and `local prepare` says so (`RUNTIME_OVERRIDE=`); a profile whose own `model` the runtime does not list is `runtime-profile-model` (give the profile a tier). `project validate` refuses a profile whose runtime is not enabled or whose model, tier or effort does not fit that runtime.
- **What a project with extras sees.** `agent for` prints a fifth word, `MEMBER MODEL EFFORT PROFILE RUNTIME`, and its JSON the key `runtime`; `agent models` a `runtimes:` line and a `RUNTIME` column, each profile resolved in its own runtime; `local prepare` the line `RUNTIME=NAME` for every run, the own runtime's too, `RUNTIME_OVERRIDE=...` where `--runtime` differs from the runtime the profile names, and `MEMBER_SKILLS=none (not delivered to an extra runtime)` for a run on an extra runtime; `local list` a `RUNTIME` column and a `model=M (requested at prepare, not confirmed)` tail, or `(requested at prepare, override verified)` when the runtime's per-dispatch model override is verified; `review check` a line `runtime=R model=M (requested, ...)` first. Both read the registry line only. No runtime reports which model answered, so the wording says requested, and a verified override is still not a report of the model that answered: it is never "confirmed".
- **A run starts on the runtime it was prepared for.** `qargi local run` takes the runtime from the registry line (a line without one was prepared without extras and means the project's own). It refuses with `runtime-drift`, nothing started, when that runtime is no longer enabled, no longer sealed, local and started by a command, or when its definition, catalog, composition, profile or policy changed since prepare: prepare again. Enabling an extra runtime stales no open run of the own runtime, whose request is byte-identical. The verbs that take a run in (`local verify`, `review check`, `review apply`, `local close`, `local clean`) ask for no runtime, so a finished run is taken in the same way after its runtime is disabled.
- **The barrier is the runtime's own.** A read-only role needs the read-only barrier of the runtime it runs on, never of the profile, and the acceptance `models.accept_no_barrier.local` was given for the project's own runtime and does not count for another. For an extra runtime a barrier that holds or is partial passes (a partial one prints its note at prepare and at run), and one with no barrier is `runtime-barrier-missing`, refused before any run is made; no acceptance record exists for extras. `local prepare` asks after it has resolved the runtime.
- **A review on `codex` is a reading review.** The read-only sandbox refuses every write, `TMPDIR` included, so a member of a read-only role on `codex` cannot run `go test`, `go vet`, a build, a linter that writes a cache or `git apply`: it reads and reports, and always runs `--sandbox read-only` (no option, profile key or answer changes that). The lead puts what is to be reviewed on disk before the run (the diff or the patch series as files, at a path the member sees, never under `/dev`), names the files in the task block, runs the tests and gates itself and puts their output beside the diff; the report can cite that output and verify none of it. A verdict from such a member is a verdict on reading. A reading review is advisory, and the practice qargi recommends is that it is never the sole review behind a merge: a second review on the project's own runtime, or the owner's, stands behind it, for these reasons: it ran nothing, its sandbox does not confine reads, and the model behind its verdict is requested, not confirmed. The owner decides whether to keep that practice; no verb checks it.
- **Notes.** The notes about members depend on the runtime a member runs on. `qargi provider notes [TOPIC] [--runtime NAME | --run RUN]` answers `spawn`, `member-out` and `message` from NAME (one the project enabled) or from the runtime the registry records for RUN, so `provider notes spawn --run RUN` says `qargi local run RUN` for a run on a command runtime and the session's tool for one on an in-session runtime. The topics about the lead's own session keep to the lead runtime. Neither option: the project's own runtime, as before.
- **Not in this release.** `qargi packs apply --target` for an extra runtime (pack renders go to the own runtime), managed member skills on an extra runtime, an in-session extra runtime, and confinement of reads.

A worked example. A project on `claude-code` enables `codex` (the owner approves with words that carry `reads are not confined`), and adds two profiles: `codex-build` (`base` `worker`, `runtime` `codex`) and `codex-review` (`base` `reviewer`, `runtime` `codex`). A build goes to `codex` with `qargi local prepare --role build --profile codex-build ...` then `qargi local run RUN`, and is taken in with `local verify`, `review check` and `review apply`. The same change gets two reviews: `qargi local prepare --role review --profile codex-review` (a reading review, with the diff and the test output on disk) and one on `claude-code`; both reports go through `qargi review check`, whose first line names `runtime=codex` and `(requested at prepare, not confirmed)` for the first. The merge waits for the review on `claude-code`, which is the one that ran the tests.
