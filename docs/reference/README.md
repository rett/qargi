# Reference

- [Backlog graph v1](backlog-graph.md) documents the native read-only schema, reports, source revision evidence and planning limits.
- [Campaign records v1](campaign-records.md) documents bounded local declarations, the closed schema, publication outcomes and bounded history.
- [verify.environment](verify-environment.md) documents the optional project answer that starts the whole-suite runs of `qargi feature verify` and `qargi release verify` under a declared environment (signals, descriptors, terminal, cpu scope, variables): the schema, the refusal codes, the waiver, the record, and a table of each setting against the hosted Linux runner it was measured on.
- [Refusals](refusals.md) is the catalogue of the rules that stop a command: each code with the rule, why it exists, its class and exit status, its status (live, planned or withdrawn), the fields of its message and the next step. It is generated from `lib/refusals.json`; `qargi help refusal [CODE]` prints the same from the command line.
- [The stored plan record](plan-record.md) documents `STATE/plans/TOKEN.json` (schema `qargi.plan/0`, a draft): what a verb keeps of the plan it printed a token for, the kind of each value, the binding to `input_sha256`, and `qargi plan show TOKEN [--json]` with its refusals.
- [Lead seat v1](lead-seat.md) is the contract of the lead handoff seat, written before the code: numbered rules with their refusals, the records, the handoff steps and the open points. The seat is not built.

## Planning reports and declarations

`qargi backlog graph check|show|why --graph FILE` reads manually declared relationships against the configured open backlog. `why` also needs `--node REF`. Reported evidence follows the parser's item digest. Feature references and archived items remain unobserved. The reports grant no approval, acceptance, scheduling or execution authority. The public command remains lead-only under the current member guard. The [graph reference](backlog-graph.md#commands-and-boundaries) describes the member-safe direct Python reader and its limits.

`qargi campaign check --spec FILE` validates a supplied declaration without configuration or state probes and is available to members. The lead owns local `commit`, stored `check`, `show` and `log` operations. Campaign records retain supplied design and briefing claims and unresolved evidence links. They do not observe source state or record acceptance. [Campaign records v1](campaign-records.md) specifies the qualified local-store boundary and bounded history. Ataniq owns its separate orchestration work. Fresh review against actual dependencies remains required before merge acceptance, and declarations do not enforce that review.

## Help, manual page and completion

- `qargi help` lists the commands by task; `qargi help COMMAND` shows its verbs and `qargi help COMMAND VERB` the arguments and options of one. Every command also takes `--help`. `qargi help concepts`, `roles`, `approvals`, `guard`, `refusal`, `naming`, `memory-stores`, `push`, `environment`, `files` and `dev` explain the ideas; `qargi help refusal` lists the codes of the refusals and `qargi help refusal CODE` prints one entry (rule, why, class, exit status, status, fields, message and next step; an unknown code exits 2).
- `--json` is a global option: on any verb it prints the result as one JSON object (the plan, its token and the command that applies it; see `qargi help approvals`). `bin/qargi` and `lib/jsonplan.py` handle it once for every verb, and `lib/commands.py` describes it as `GLOBAL_OPTS`; a verb that describes a `--json` of its own keeps it.
- `man qargi` is the complete reference (`qargi help --man | man -l -` if it is not installed).
- Tab completion for bash, zsh and fish offers commands, verbs, options (each once, also as `--option=value`; with a one-line description in zsh and fish) and the values that exist on your machine, each with its description in zsh and fish: your projects (for `lead` and `team`, those that define teams), instances (cloud ones for `start`, `send`, `track`, `instances budget`), sessions narrowed to what the verb can act on (`stop` a running one, `collect` one whose outputs are not downloaded, `close` and `watch` the open ones), a project's teams, roles and packs (skills or tools by command), memory store and deployment ids, model ids, the branches of the project's repository for `--base`, the keys of a project's answers for `project set` with the values each takes, and the usual spend ceilings and wait times. `install.sh --user` installs all three; zsh needs `fpath=(~/.local/share/zsh/site-functions $fpath)` in `~/.zshrc` before `compinit`.
- Inside a project's repository you can leave out the project: `qargi lead status`, `qargi team brief code-docs ...`, `qargi canon check`. A role stands for the instance: `qargi instances show build`. `QARGI_PROJECT` names the project from anywhere. A project you type always wins.

All three, and the checks that keep them true, come from one description of the commands in `lib/commands.py`; `tests/test_help.py` compares it with the scripts. After changing a flag or a verb, describe it there and regenerate the page with `python3 lib/help.py man --keep-date man/qargi.1 > man/qargi.1.new && mv man/qargi.1.new man/qargi.1` (a plain `> man/qargi.1` empties the file before the date in it is read).
