# Release documentation review

Review the authorized documentation scope against concrete source, release and ref evidence. Record the exact commit, tree, tag or ref, release status and evidence location for each material claim. Keep the owner's selected release target separate from published availability.

- Classify capabilities as implemented, qualified, limited or planned. Distinguish source observations from deployed observations. Inspect examples, shared option descriptions, file references, generated sections and supported platform scope.
- Trace clone, credential, sandbox, guard and ref-verification claims through the selected runtime's source, contract and recorded checks. State each protection's measured boundary and remaining gaps. Avoid claims of impossible pushes, all-provider isolation, universal portability or verification of every command.
- For changed skill, tool, provider, catalog or extension packs, inspect applicable content, compatibility and activation records. Distribution, proposal hints and seeding leave adoption to existing approval workflows.
- Report what link, code and render tests measured, including exact inputs, commands, results and skips. Obtain separate evidence for live publication observations. A passing source check alone cannot establish deployed availability or perpetual currency.
- Retain exact supporting evidence and unresolved gaps for lead disposition. Propose corrections within scope. Preserve owner permission, independent source review, release and website gates, and session and rollout gates. Leave integration, publication and activation to their authorized owners.
