Load when you render or apply packs, link a project or repository, or handle unmanaged skills.

# Apply and link

Every apply here prints a plan and a token first; show the person the plan and wait for their go-ahead before `--plan TOKEN --approved "..."`.

Select a local target through the existing registry's `session.render_target`. The member runtime resolves directly; a secondary target needs exactly one valid, sealed local definition with verified skills support and a project layout. Unverified claims or inapplicable project extensions refuse. Member selection and profiles stay unchanged; apply without a target retains the cloud route.

Renders live side by side under `render/PROJECT/RUNTIME`. Plans name project, runtime, target, compatible included/skipped packs and resources; tokens bind that identity and the composed definition. Foreign metadata refuses; metadata without runtime identity is supported only for the default runtime, then strengthened by a fresh plan. Lead-only instructions load as skills without joining the member MCP permission union.

Applicable sealed extensions compose on the selected secondary runtime with verification bound to that base; missing, unsealed, drifted, inapplicable, unmet or conflicting extensions refuse loading. Owned unlink and backup restoration, including combined project unlink, survive lost skills support or verification and harmless library-provider reseals, composition changes or manifest corruption. Cleanup needs valid unambiguous sealed runtime identity, consistent sealed extension composition, a safe skills path/link mode and exact ownership/backup guards. It skips current pack reviews and capability-verification prerequisites. Default cleanup preserves omitted target and mode fields accepted by its existing link routes. Explicit secondary targets retain their target identity and dir-symlink mode checks. Conflicting sealed extension resources can refuse cleanup, including combined unlink of another resource. Per-resource cleanup isolation remains planned. Missing, ambiguous, unsealed or drifted identity and unsafe layouts refuse; never guess old paths. Fresh apply/check/link stay strict. Unaccept needs unambiguous runtime/target identity even after skills support, verification or layout is lost. Accept tokens bind project/runtime/target/composition; unaccept tokens bind the exact provider record and scope. Obtain a fresh plan when either changes. Every included skill, including lead-only instructions on every local target, needs prior canonical library approval matching its content hash. Passing review or approving a render cannot replace absent approval; refusal preserves the live render. Missing or empty tool approvals grant no MCP tools; rendering shares member approval and policy checks.

- **New instances:** `/qargi-provision` attaches the role's packs: custom skills are uploaded, and tools become MCP servers with their policies; the plan token covers their content.
- **Existing cloud agents:** `qargi packs apply INSTANCE --asked "..."` prints the plan and a token; with `--plan TOKEN --approved "..."` it uploads the custom skills, replaces the agent's skill, MCP-server and tool lists (a new agent version) and re-points the deployment. Vault ids a tool needs are reported, not attached.
- **A local session:** `qargi packs apply --target TARGET PROJECT` prints additions, changes, removals, incompatible packs, shadowing and credential needs. With token and approval it renders to the selected runtime's state directory, using its skill, MCP and settings paths, and prints its launch line when defined. The configured state directory receives the render. Role scoping stays advisory. Configure reported vault credentials yourself. `qargi packs check --target TARGET PROJECT` checks drift, shadowing, file modes, permissions, manifest and visible skills without editing them. Hostile packs refuse the plan.
- **Repo link:** `qargi packs link PROJECT` (plan token, then `--plan TOKEN --approved "..."`) makes the checkout's skills directory (the runtime's `resources.skills.project_dir`) a symbolic link to the render, so a session there loads the project's packs with no `--add-dir`. A real directory is moved to `skills.qargi-backup` (never deleted) and the plan lists its skills as same, differs or new; offer `skill import` and `skill link` for the new ones. `packs unlink PROJECT` undoes it. Git-tracked skills, a foreign link and a symlinked parent are refused. The link is not tracked, so each worktree needs its own. A project must name its provider (`models.provider`); there is no default. If a link stops half way, the message says where the skills are; `packs unlink PROJECT` moves a backup back when its link is gone.
- **Skills, agents and memory together:** `qargi project link PROJECT [--resource skills,agents,memory]` is the same engine for all three in one plan and one token; `project unlink` undoes it. Run it inside the work tree to link (each worktree has its own links; nothing records which exist). Each resource is linked the way the runtime's definition says (a directory link, one link per entry, or a copy), and a real directory in the way moves to `NAME.qargi-backup`. `packs link` is the skills part alone. See `/qargi-project`.
- **Secondary checkout skills:** use `qargi packs link PROJECT --target TARGET`, then `qargi packs unlink PROJECT --target TARGET` to undo it. Only skills with `link.project: dir-symlink` are supported here. Distinct paths coexist; foreign links and tracked destinations refuse, and unlink restores only that target's backup. Without a target these verbs retain the member runtime. `project link|unlink` takes no target.
- **Secondary approvals:** add `--target TARGET` to `qargi skill accept|unaccept PROJECT NAME [--user]`. Resource/provider/name approvals are independent, including user scope; removing one preserves another provider's approval. Unowned records approve nothing for a provider-bound audit. Exclusions follow the selected runtime's resources and settings.
- **Unmanaged skills:** `packs check --target ...` ends with every skill a session would load, as `qargi`, `accepted`, `drifted`, `excluded` or `unmanaged`. Show the person the `unmanaged` ones. `qargi skill accept PROJECT NAME [--user]` records one they want (name and content hash; the plan shows the import review); `skill unaccept` removes it. An accepted skill that changes is `drifted` and fails `check`. To switch a skill off without removing it the person sets the runtime's exclusion in their settings (`qargi provider notes skills-dir`; another runtime may use a config list or a deny list); qargi only reads those files. For an `unmanaged` skill the section prints the line to add (`to hide it instead: ...`), as text built from the provider's layout, and never writes it.
